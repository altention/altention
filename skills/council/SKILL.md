# Council — 會演進的多視角議會

靈感來自 Tobi Lütke 的做法：重要決定交給一個由 5–6 位不同背景專家組成的小議會，各自獨立分析，隨機指定一位綜合，最後由最強的模型讀完全部內容，交回給人做決定。再加上 Shopify River 的「做夢」機制：定期回顧自己的表現，把教訓寫回 skill 檔案。

兩個核心信念決定了這個 skill 的形狀：
1. **機器不能負責，人才能負責。** 議會的產出是「決策面板」，把選項、取捨、關鍵不確定性攤開，讓使用者能好好判斷。可以給建議，但要清楚標示「最後由你決定」，也不要假裝有確定答案。
2. **不要丟垃圾手榴彈（slop grenade）。** 議會內部可以很長，交給使用者的只能是濃縮後的精華。讀的人的注意力是最稀缺的資源。

本 skill 的目錄（以下稱 `$COUNCIL`）就是 `~/.claude/skills/council/`。它通常是一個 symlink，指向引擎（預設 `~/altention/engine`）裡的 `skills/council/`。使用者會在多台伺服器上工作：議會的記憶（`data/`）放在使用者的實例裡，由同步在各台機器之間傳遞。

## 資料在哪
- `$COUNCIL/data/`（`profile.md`、`lessons.md`、`CHANGELOG.md`、`runs/`）是使用者自己的資料，放在實例裡，`data/` 是指向實例的資料夾連結。直接讀寫這些路徑就好；**不用自己 git add、commit 或 push**，實例的同步每 15 分鐘會自動提交並傳到其他機器。
- 開始時可以跑引擎的 `bin/home-pull --quiet` 拿到最新的程式和角色檔（失敗就提一句，繼續）。

## 模式判斷

- 使用者帶著一個問題或決定來 → **議會模式**（下方流程）。
- 使用者說 "council dream"、要議會反思、整理、演進 → 讀 `references/dream.md`，執行**演進模式**。

## 議會模式

### 0. 載入累積的經驗
先讀 `$COUNCIL/data/profile.md`，了解使用者的背景、常見決策類型和輸出偏好；再讀 `$COUNCIL/data/lessons.md`，這是過去每次執行後留下的教訓，比本檔案的預設更新，衝突時以它為準。最後列出 `$COUNCIL/roles/` 看有哪些角色可用（`_retired/` 除外）。

**議會只討論，不動手**：整個流程裡，包括所有 sub-agent，都不修改程式碼、不 commit、不碰正式環境或共用資源。唯一的例外是寫入 `$COUNCIL` 自己的紀錄。

### 1. 釐清問題（最多問一次）
把使用者的問題改寫成一個**決策問題**：要決定什麼、有哪些限制、什麼算成功、時間尺度多長。若缺少會大幅改變結論的關鍵資訊（例如預算、時間、底線），一次問完，最多 3 個問題；否則直接做合理假設並寫明。

如果使用者已經說出自己的推論或傾向，把它記下來，當作「使用者目前傾向」一併交給議會。使用者問「你覺得呢？」時，多半想要的是被挑戰或被確認。

### 2. 組成議會
預設 4 個角色，只有高風險或跨領域的題目才用到 6 個。使用者在意額度，說「快速議會」時就只用 3 個角色，全部用 sonnet。`contrarian`（唱反調）和 `empiricist`（實證者）幾乎每次都要出席：前者抵抗共識偏誤，也負責挑戰使用者自己的傾向；後者為每個選項找出最便宜的驗證方式。`long-term` 用來抵抗「選有快速回饋的那條路」的短視。研究題加上 `reviewer`，產品或 API 題加上 `user-advocate`。問題需要但缺少的角色，可以臨時定義，並在事後的反思中決定要不要存成新角色檔。

**模型多樣性**：不同模型有不同盲點。派 sub-agent 時用 Agent 工具的 `model` 參數把角色分散到不同模型，不要全部用同一個。為了節省額度，大部分角色用 sonnet，其中 1–2 個關鍵角色改用 opus 或 fable。

### 3. 平行獨立分析
在**同一則訊息**中平行派出所有角色（Agent 工具，general-purpose）。每個 prompt 包含：
- 該角色檔的完整內容（直接貼上，sub-agent 不一定讀得到）
- 決策問題與背景、已做的假設、使用者目前傾向（如果有）
- 可用資源：若問題牽涉目前專案的程式碼或檔案，告訴它路徑；需要外部事實時可以上網查
- 輸出格式要求（控制在 400 字內）：
  ```
  立場：一句話
  核心論點：3–5 點，每點附依據（資料、來源、推理）
  最大風險／我可能錯在哪：
  我會想先驗證的一件事：
  信心：低／中／高，與原因
  ```
  另外提醒 sub-agent：用繁體中文、白話；術語第一次出現就附一句解釋；終端機輸出不用 LaTeX；把證據和推測分開標示。

角色之間互相看不到彼此的答案，這樣才是獨立意見，不會在第一輪就被群體思考拉走。

### 4. 隨機綜合
用 `python3 -c "import random,sys; print(random.choice(sys.argv[1:]))" <角色名...>` 從出席角色中隨機選一位當綜合者，再派一個 sub-agent（換一個跟它原本分析時不同的模型）扮演該角色，讀取**全部**立場，產出：
- 共識點與真正的分歧點（分歧的根源是事實不同、價值不同，還是假設不同？）
- 可行選項清單（通常 2–4 個「都說得通」的選項）

隨機指定綜合者是為了避免永遠由同一種視角來定調。

### 5. 裁決：產出決策面板
由你（主模型）讀完所有原始立場和綜合結果，自己判斷綜合者有沒有漏掉或扭曲少數意見，然後交給使用者：

```markdown
## 決策面板：<問題>

**在決定什麼**：一句話複述問題和限制（理解錯了，使用者可以馬上指出）
**一句話結論**：建議選 X，因為…（但由你決定）
**對你目前傾向的看法**：（使用者有表達傾向時才寫）議會支持還是挑戰它，理由是什麼

### 選項
| 代號 | 做什麼 | 最大代價／風險 | 最便宜的驗證方式 | 可逆嗎 |
|---|---|---|---|---|
| A | … | … | … | … |

### 議會真正的分歧
- …（說清楚分歧來自事實、價值還是假設）

### 值得警惕
- 最多 2 點，只寫真正值得注意的地方。例如最容易被忽略的少數意見；或者某個選項是「業界標準做法」或「回饋最快」，要特別檢查它是否只是看起來安全

### 下一步：先驗證這件事
- 能最快降低不確定性的一個行動

<details><summary>各角色原始立場</summary>…每位 2–3 行摘要…</details>
```

整份面板要在一個螢幕左右讀完，使用者想看完整內容時再展開。選項用 A/B/C 代號，讓使用者可以直接回「選 B」。其他寫作要求：
- 繁體中文、top-down、白話
- 術語第一次出現就用一句話解釋
- 不用 LaTeX，也不用 emoji
- 證據和推測要分開標示，研究類主張附上來源

### 6. 記錄與反思（每次都做，這是演進的燃料）
交付面板後：

1. 寫一份執行紀錄到 `$COUNCIL/data/runs/YYYY-MM-DD-<hostname -s>-<slug>.md`（檔名加上主機名，避免不同機器寫出同名檔案）：問題、出席角色與模型、綜合者、結論、以及**你對這次議會本身的觀察**（哪個角色貢獻最大或最空洞？有沒有角色重複？問題框架有沒有問題？花費是否值得？）。
2. 如果這次暴露出一個**可泛化**的教訓，就在 `data/lessons.md` 追加一行，格式為 `- [YYYY-MM-DD] 教訓（證據：data/runs/檔名）`。只寫下次真的會改變行為的事；只對這一題成立的細節不要寫。
3. 在回覆最後用一行邀請使用者回饋，例如「這次哪個角色最有用或最沒用？回饋會讓議會變得更好。」使用者之後給的回饋，追加到該次 run 紀錄的 `## 使用者回饋` 段落，並視情況更新 `data/lessons.md`。

`data/` 底下的修改不用自己提交（見上方「資料在哪」），同步會處理。

不要在議會模式裡大改角色檔。結構性的調整留給演進模式，那時才看得到跨多次執行的模式，而不是對單次結果過度反應。

## 檔案地圖

- `data/profile.md`：使用者背景與偏好，每次都讀
- `data/lessons.md`：累積的教訓，每次都讀
- `roles/*.md`：角色定義，各自帶有「演進筆記」段落
- `data/runs/`：每次執行的紀錄與使用者回饋
- `references/dream.md`：演進模式的完整流程
- `data/CHANGELOG.md`：每次演進改了什麼、為什麼
