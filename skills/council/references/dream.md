# 演進模式（Dream）

就像 River 在夜裡回顧當天的對話：看自己在哪裡卡住、犯了什麼錯，然後改寫自己的 skill 檔。這是一次對自己的 post-training，只不過產出是文字檔。

觸發時機：使用者要求，或 `data/runs/` 裡自上次演進後累積了 5 筆以上的新紀錄（議會模式結束時可以提醒使用者）。

## 流程

### 1. 收集證據
- 讀 `data/CHANGELOG.md` 找出上次演進的日期
- 讀那之後的所有 `data/runs/*.md`，**特別是有「使用者回饋」的**。使用者回饋的權重遠高於你自己的觀察，因為最後承擔結果的是他們
- 讀目前的 `data/profile.md`、`data/lessons.md`、全部 `roles/*.md`，以及 `SKILL.md`

### 2. 找模式，不是找個案
逐一回答：
- 哪些角色常常提供獨特且被採用的洞見？哪些常常空洞、跟別人重複？
- 有沒有反覆出現、卻沒有角色負責的視角？（→ 新角色候選）
- 使用者反覆抱怨什麼？（太長、太保守、沒回答真正的問題、太貴…）
- `data/lessons.md` 裡有哪些教訓已經被證實、已經過時，或者互相矛盾？
- 流程本身（`SKILL.md`）有沒有哪一步經常被跳過、或做了也沒價值？
- `data/profile.md` 裡標為「推測」的項目，哪些已經被實際執行證實（移除「推測」標記）？哪些被推翻（刪除）？

只出現一次的現象先不要動手改，除非它是使用者的明確回饋。

### 3. 修剪優先於增加
「你不能靠一直加東西讓事情變好，你必須修剪。」
所以編輯順序是：
1. **刪**：過時或矛盾的教訓、從沒發揮作用的角色（移到 `roles/_retired/`，不要直接刪，保留可以回溯的歷史）
2. **合併**：重複的教訓合成一條更精確的原則；把已經穩定的教訓升級寫進對應的角色檔或 `SKILL.md`，再從 `data/lessons.md` 移除
3. **改**：調整角色的提示、重點與盲點
4. **加**：真的必要時才新增角色或規則

`data/lessons.md` 保持在 30 條以內。超過就代表該整併了。

### 4. 版本控制與記錄
`data/` 底下的檔案在實例裡，由實例的同步自動提交，不用自己 git add、commit 或 push。演進前先跑引擎的 `bin/home-pull --quiet` 拿到最新的程式和角色檔；其他機器的紀錄由同步帶過來（最多 15 分鐘）。

`roles/*.md` 和 `SKILL.md` 還在引擎裡（使用者自己的覆蓋層是階段 4 的事）：這次對它們的修改留在工作樹、不要自己提交，結束時列出改了哪些檔，告訴使用者請開發頻道審過再提交。

在 `data/CHANGELOG.md` 最上方追加一條：日期、改了什麼、依據哪些 runs 或回饋。

### 5. 回報
用 5 行以內告訴使用者這次演進改了什麼、為什麼，並提醒 `data/` 的歷史在實例的 git 裡（`git -C ~/altention/instance log -- skills/council/data`），可以從那裡找回舊版。

## 界線
- `SKILL.md` 的 frontmatter（name、description）只有在使用者同意時才改，因為它決定 skill 何時被觸發，改錯會讓整個 skill 失效。
- 不要刪除 `data/runs/` 紀錄；它們是證據。
- 兩個核心信念（人負責、不丟垃圾手榴彈）不在演進範圍內。
