# dcbot：給「修改機器人自己」的 Claude 看的說明

你就是這個 Discord 機器人，也是 Altention 的核心：使用者在 Discord 上管理 Claude Code 對話的地方，跟使用者其他機器上的 Claude 共用同一份知識和工具。使用者在開發頻道（工作目錄是引擎的頻道，使用者要用時才開，名字隨使用者）跟你說要加什麼功能，你在引擎的 `dcbot/` 裡改自己的程式。

這份說明是公開的，寫的是每個安裝都成立的事。**不要在這裡寫個人內容**（機器名、帳號、頻道名和 ID、對話名、私人 repo 網址、使用者的偏好）；那些寫在實例附錄。範例一律用假值：ID `1000000000000000xx`、機器 `host-a`、帳號 `alice`、頻道 `#project-a`。

- **引擎**：`dcbot/` 的上一層資料夾，下面寫的 `bin/`、`ops/`、`altention/` 都相對於它。
- **實例**：使用者的私人設定和資料。位置：在引擎資料夾執行 `python3 -c "from altention import config; print(config.instance_dir())"`，印出 `None` 表示這台還沒有實例。
- **實例附錄**：`<實例>/dcbot/CLAUDE.md`。這個安裝特有的事（有哪些機器、各台的怪癖、使用者的習慣、踩過的坑）。有這個檔就在開始改之前讀它；學到只屬於這個安裝的事也寫回那裡，不要寫進這份。

## 架構
- `bot/main.py`：Discord 用戶端。只聽擁有者（OWNER_ID），每個頻道對應一個持續的 Claude Code 對話（`state/channels.json`）。內建指令 `!status !reset !resume !recap !commands !attach !detach !stop !cwd !mode !screen !key !restart !rollback` 不經過 Claude，是壞掉時的救命繩，**不要拿掉**。
- 每個頻道有兩種模式（`!mode`，預設 `tmux`）：
  - **tmux 模式**（`bot/tmux_bridge.py`）：Claude Code 以互動模式活在 tmux 裡（機器人自己的 tmux server：`tmux -L dcbot ls`、`tmux -L dcbot attach -t <名稱>`）。行程不屬於機器人，所以機器人重啟／部署不會打斷對話，背景工作跨輪存活，處理中途可以補充訊息。
    - **窗格物件**（`tmuxio.Pane`，3b 2.4a）：開對話的那幾處經過它讀畫面、按鍵、問還在不在、收掉自己開的；它不做決定，每個方法就是 `tmuxio` 同名的函式（呼叫時才查，所以 `fakepane` 的替換照樣有效）。測試要直接給一個窗格時用 `fakepane.Pane(fake, 目標)`。打字、選單、btw 還沒經過它（2.7a）。
    - **開對話**（3b 2.4b）：指令列和設定檔在接頭 `launch.py`（旗標的名字只在那裡；`launch.permissions()` 是合法的權限模式，照 2.1.296 的 `--help`）。`TmuxBridge.open()` 是唯一的一份迴圈（先試接回、不行開新的、等好、失敗收掉），三種頻道差的只有它拿到的三個小函式（怎麼開、開成之後記什麼、沒開成怎麼收）。**模型和權限**：頻道狀態的 `model`／`permission` → 這個安裝的設定 `dcbot.default_model`／`dcbot.default_permission`（`plugins.json`）→ 現在的值（`config.MODEL`、bypass；後者是待辦，階段 6 D-03）。權限值不合法、或讀不到安裝的設定：**不開對話**並在頻道說明（讀不到的那句說是哪個檔、修好再傳一則就會開）（不退回預設值：預設是全部放行）；模型讀不到設定時用現在的值。不合法時的那句話說是誰的值（頻道的，或安裝設定 `plugins.json` 的 `dcbot.default_*`）；模型的值不是文字也不開。設定檔讀得出來時當場讀（訊息到開視窗之間不讓別的事件插進來）；讀不出來時才丟到執行緒（引擎讀到壞檔第一次會等 0.4 秒），不在事件迴圈裡等。**print 模式的頻道目前不吃這兩個設定**（`claude_bridge.py` 仍寫死；記給 2.9）。開不起來的每一種原因是 `NotOpened`（`BridgeError` 的子類別）：`why` 代號＋`data`，字照舊（2.6 之後用代號）。`state/claude-settings.json` 內容沒變就不重寫。測試：用假窗格的測試一律不讀真的安裝設定（`fakepane` 設 `ALT_INSTANCE=-`）。
    - 輸入：`bot/tmuxio.py` 用 `send-keys -l` 逐行打字（行間 Alt+Enter），再按 Enter。**不要改成貼上**：長的貼上會被包成 `<pasted_content>`。
    - 輸出：不抓畫面。`state/claude-settings.json`（啟動時產生，只套用在機器人開的對話）掛了 hooks，由 `tools/dchook` 把每個事件寫成一個檔案放進 `state/events/`，`tmux_bridge.pump()` 讀出來貼到 Discord。`UserPromptSubmit`＝訊息送達（加 👀）、`PreToolUse`＝進度、`Stop`＝貼出最後一則回覆。
    - 中途的話：`Stop` 只帶最後一則文字。Claude 在工具呼叫之前說的話要從對話紀錄（事件裡的 `transcript_path`）讀：每個 `PreToolUse` 和 `Stop` 時用接頭的 `transcript.new_texts()` 讀出上次之後新增的文字，以引用樣式（`>>> `）貼出。每輪開始時把讀取位置移到檔尾，並略過跟最後回覆相同的文字，避免重複貼。設定 `INTERIM=0` 可關掉。
    - 失敗：API 出錯時沒有 `Stop`，而是 `StopFailure`（`error`：rate_limit、authentication_failed、billing_error、invalid_request、server_error、max_output_tokens、unknown；錯誤訊息在 `last_assistant_message`）。2.1.289 實測互動模式會觸發。`TmuxBridge.failed()` 貼出原因和「再試一次」按鈕（`retry:<頻道>`，送一句 `RETRY`）。
    - 通知：中途的話、進度訊息、⌨️／📤／📨 都 `silent=True`；正式回覆、提問、計畫、選單、失敗會響。超過 `LONG_TURN` 秒的一輪在頁尾加上 `<@擁有者>`。
    - 立刻送出（`!!` 開頭的訊息，`submit(now=True)`）：照常打字送出，Claude 忙時訊息會排隊並顯示「ctrl+x ctrl+s to send now」，`send_now()` 看到這行才按 `C-x C-s`。實測（2.1.289）：正在跑的 Bash 被移到背景，Claude 同一輪讀到訊息並回覆，`UserPromptSubmit` 在排隊時就已經觸發。
    - context 佔用：接頭的 `transcript.context()` 從對話紀錄最後一則主對話回覆的 `usage` 算（input + cache read + cache creation，跟 Claude Code 狀態列的算法一樣），視窗大小 `events.window()`：haiku 200k、其他 1M（2.1.289 狀態列輸入的 `context_window_size` 實測）。存在 `st["context"]`，顯示在頁尾和 `/status`；別台機器的由 `dcremote stream` 在 `Stop` 時算好帶回。
    - 訊息和回覆不是一對一（補充訊息共用一輪；背景工作完成會自己開一輪），所以規則是「每個 `Stop` 都貼」。Esc 中斷不會有 `Stop`。
    - 畫面只用在這幾個地方：啟動時回答信任資料夾的對話框、`!screen`／`!key`、判斷是否還在忙（`esc to interrupt`）、`/` 指令（例如 `/usage`）送出後回傳畫面，以及打字前偵測面板還開著就先按 Esc 關掉。面板的判斷是「看到 `Esc to cancel` 之類的提示，或畫面上沒有輸入框（橫線下一行以 `❯` 開頭）」：面板比畫面高時提示那一行會被擠出畫面，只認提示字樣會漏掉。Claude Code 改版後這些字樣可能會變。**機器人自己開的對話也照同一個原則（2026-10-09 起；使用者可以 `tmux attach` 直接坐在那裡，權限模式不是 bypass 時也會跳權限詢問）**：只有一般的輸入框有鍵盤時才打字、才按 Enter；`!` 模式或有對話框就不按任何鍵、在頻道說；只有機器人自己的指令打開的面板（`st["own_panel"]`，存在頻道狀態裡，機器人重啟後還在；任何一輪的事件一來就不算）才先按 Esc。跟接上的窗格不同的只有兩點：框裡留下的字照舊清掉（那是機器人自己的對話）；第一次按 Enter 前框裡的字跟打的對不上時照樣按（日誌印一行 `[enter] …`，並記進 `state/enter-differs.json`，doctor 的 `dcbot.enter-differs` 一週三次以上會 warn），免得 Claude Code 畫字的方式比對不認得時所有頻道都送不出去；回條沒到的重試只在框裡還是那則訊息時才按。上一則按了 Enter 卻還留在框裡時，自己的對話會清掉、重打、重送並在頻道說一句（接上的窗格不動、警告）。**畫面上固定字樣的判斷，一律只看 Claude Code 自己畫的區域**（manager 2026-10-09）：輸入框結束那條橫線以下（狀態列、面板提示；沒有輸入框時是畫面最後幾列），用 `screen.under_box()`；「在忙」只問 `screen.busy_shown()`，面板和對話框只問 `panel_shown()`／`pane_state()`。任何會出現使用者或 Claude 文字的地方（框上方的對話內容、輸入框裡的字）都不看：回覆引用「Esc to cancel」曾讓閒著的頻道所有訊息被擋，訊息自己寫到這幾個字曾讓它打進去後不按 Enter，內文寫到「[Pasted text]」曾被記成貼上。新增這類判斷、或審查它時，要用「內文自己含那些字」的訊息和回覆實跑。**接上的窗格（`/attach`、別台機器）是使用者自己的終端機，打字前不替他按鍵**（`may_type()`、`pane_state()`）：只有一般的輸入框有鍵盤時才打字；輸入框在 `!` 模式（打進去會當 shell 指令執行）、或有對話框／選單開著（權限詢問：打字加 Enter 等於選 Yes，Esc 等於選 No）就不打字、不按任何鍵、在頻道警告。只有機器人自己送的 `/` 指令或 `/btw` 打開的面板（`rt.own_panel`，任何一輪的事件一來就不算）才會先按 Esc 關掉。`/btw` 打字前走同一套檢查，打完之後框裡不只是它自己打的那段（`screen.bot_typed()`）就不清。接上的窗格每一次 Enter 之前（第一次、回條沒到的重試、`/btw`）都再讀一次畫面（`enter()`）：一般的輸入框、框裡正好是機器人打的那段才按；那台的事件連線斷著時不重試、也不算 `own_panel`。「正好是機器人打的那段」的比對（`screen.bot_typed()`）：空白不計、NFC、去掉 Claude Code 畫的時候會丟的字元；長訊息變成的 `[Pasted text #N]` 標記各代表一段（數量不超過 `screen.paste_marks()`，帶「+N lines」的是使用者貼的）；三列以上的框只比結尾（框會捲動）。已知限制：使用者在機器人打長訊息的那幾秒貼上單獨一長行、或打在被捲出畫面的上半段，看不出來。連發的訊息：框裡還是上一則剛按過 Enter 的字就等它消失（`rt.entered`，最多 5 秒）。
    - **`/btw` 的答案框、它的「x to clear history」、啟動時的對話框也只看 Claude Code 自己畫的地方（2026-10-11，#code-review-2 在 2.1.296 實跑出誤判後）**：答案框畫在輸入框原本的位置（所以有答案框時沒有輸入框），上緣是從最左邊開始的一列 `▔`，接著是問過的問題、縮排更深的答案，畫面最後一列是它自己的提示（結尾 `Esc to close`）；`screen.btw_box()` 是唯一說「答案框在哪、裡面是什麼」的地方，`btw_answer()`、`btw_hint()` 只讀它。「答好了」只看答案框自己的提示列有沒有 `c to copy`（2026-10-12：請求失敗重試時那一列是 `· API error · retrying in 2s · attempt 3/10`，不是 `Answering…`，只認字會把重試中的框當成答案、把它關掉；樣本裡提示列有 `c to copy` 的恰好就是有東西可複製的）。沒答好的框機器人不按任何鍵：等到上限就說「還沒有答案、沒有關它」，下一則訊息送出前才關。啟動對話框（信任資料夾、bypass 警告）由 `screen.startup_key()` 判斷：沒有輸入框、最後一條橫線之後的列以「No, exit」和一個 Yes 兩個答案結尾（後面只能有提示列）才按鍵。對話內文、答案內文、使用者的訊息裡出現這些字都不算。真實畫面樣本在接頭的測試旁邊 `altention/tests/connectors/claude_code/screens/<版本>/`（同一個資料夾的 `samples.py` 讀），改讀畫面的函式要對著它們跑（`tests/test_screen_samples.py`、`tests/test_screen_words.py`）。
    - Claude Code 2.1.296 起不給 `--permission-mode` 時預設是 auto mode（狀態列「auto mode on」，工具直接跑不問），權限詢問多一項「Yes, and switch to auto mode」。機器人開的對話都明確帶 `bypassPermissions`，不受影響；接上的窗格是什麼模式由使用者決定，機器人不判斷。
  - **print 模式**（`bot/claude_bridge.py`）：每則訊息跑一次 `claude -p --resume <session>`。是備用方案，tmux 模式出問題時用 `!mode print` 切過去。
- `bot/slash.py`：註冊在 Discord 的 `/` 選單（只在這個伺服器）。內建指令走 `Bot.command()`，跟 `!` 指令是同一份程式；`/usage`、`/context`、`/compact` 則是打進 tmux，跟文字訊息 `/usage` 一樣。註冊過的指令是「互動」不是訊息，3 秒內要回應，所以一律先 defer 再用 follow-up 回覆。指令內容有變才會重新向 Discord 註冊（`state/slash-synced` 記著上次的內容）。沒註冊的 `/` 指令照舊當文字送。加新的內建指令時，`!` 版本一定要有，`/` 版本看需要。
- `bot/routes.py`：路由，讓頻道接上**使用者自己在 tmux 開的** Claude Code（`!attach`／`!detach`）。對話的地址是 tmux 窗格 `{"socket": socket 路徑, "id": "%3"}`，存在頻道狀態的 `pane`；`tmuxio` 的每個函式都同時接受「機器人自己開的 session 名稱」和「窗格地址」。
    - 去程：對那個窗格 `send-keys`。打字前 `tmuxio.alive()` 會確認窗格還在跑 Claude，回到 shell 了就不打（不然訊息會被當成指令執行）。
    - 回程：`tools/dchook --install` 把 `dchook --global` 裝進 `~/.claude/settings.json`，這台機器上每個 Claude Code 都會呼叫它；它用 `$TMUX`、`$TMUX_PANE` 去 `state/routes.json` 查自己的頻道，查不到就安靜結束。設定檔的修改對已經在跑的對話也立即生效，所以 attach 不用重開對話。
    - 背景對話（Claude Code 的 agents 檢視）：窗格裡跑的是 `claude attach <id>`，只是個檢視器，對話本身在 Claude Code 的 daemon 底下跑，hook 既沒有 `$TMUX_PANE` 也不是窗格行程的後代。綁定時接頭的 `sessions.attached_session()` 從窗格行程的指令列讀出對話 id，記在路由的 `session`；`dchook` 用窗格對不到時改用事件的 `session_id` 比對（`routed_session()`，不做 nested 檢查，因為 daemon 底下本來就有好幾層 claude）。
    - **窗格的對話被搬到背景**（3b 2.4d，#issues 32）：輸入框空的時候在終端機按一次「←」（頁尾「← for agents」），窗格的對話就搬到 Claude Code daemon 底下的背景行程繼續：新的 session id、hook 的環境沒有 `TMUX_PANE`、SessionStart 的 `source` 是 `fork`，事件裡沒有任何欄位指回原本的對話；一輪跑到一半按，那一輪的 Stop 帶新 id、沒有 `prompt_id`，舊 id 不會有 Stop。連得回去的只有窗格那個行程的 `sessions/<pid>.json` 多的 `parkedJobId`（新 id 前 8 碼，比 fork 的 SessionStart 早 0.35～0.5 秒寫，之後不變）。`dchook --global` 在「沒有窗格、路由也查不到這個 session」時才讀（`routed_parked()` → 接頭 `sessions.parked()`）：那個行程還活著、它記的窗格編號是路由那個窗格、路由記的行程是它或它的上層，三樣都對才送，並在事件上標 `dc_parked`；**hook 不寫任何檔**；這台沒有任何接上的窗格時連接頭都不載入。機器人收到帶標記的事件：頻道的 `session_id` 換成新的、進行中的那一輪接著算（回覆和頁尾照常）、在頻道狀態記 `st["parked"]`（`parked(st)`：只對當時那個窗格有效；窗格自己的 Claude Code 再開對話或結束就清掉）並寫 `state/panes-parked.json`（給之後「需要注意的事」讀）。之後打字等不到回條時說的是「這個窗格的對話已被搬到背景；窗格現在可能在看別的背景對話，或停在清單…」，並在那個檔記 `unanswered`。**認不到的**：在清單裡打字開的新背景對話（Claude Code 沒有任何檔記著它跟哪個窗格有關，也沒有檔記窗格現在顯示哪一個；窗格行程的 sessions 檔在 `parkedJobId` 之後一個欄位都不再變）；`/bg`（窗格行程先結束才 fork：沒有活著的行程記著它，照「對話結束了」，下一則訊息接回原本的 id，fork 出去的那份在背景對不回來）。
    - **機器人自己開的視窗被搬到背景**（同一步）：背景行程帶著那個視窗的 `--settings` hook 和 `DCBOT_ROOT`／`DCBOT_CHANNEL`，沒有 `TMUX_PANE`；**被搬走的對話、Claude Code 預備的空背景行程（按 ← 那一刻就發 SessionStart）、清單裡打字開的每一個對話，三種都帶同一個頻道 id**（量測 2.1.288／2.1.296）。在這之前預備行程會把頻道記的 session id 蓋掉、清單開的對話的每一輪會貼進頻道。現在 `dchook`（不帶 `--global` 的那條路）遇到「沒有窗格、環境有 `CLAUDE_JOB_DIR`」的事件才多做一件事：用同一個 `sessions.parked()` 找記著它的窗格行程，從**那個行程自己的環境**讀 `TMUX`／`TMUX_PANE`（Linux `/proc/<pid>/environ`；macOS `ps eww`，**未實測**）填成 `dc_pane`、標 `dc_parked`，之後照現有的 `from_elsewhere()` 判斷是不是頻道現在的視窗。**找不到或讀不到的不在 hook 丟**（#code-review-2 實測：視窗自己的 Claude Code 先結束之後，被搬走的對話會在 daemon 底下把那一輪跑完，而那時已經沒有任何行程記著它；丟掉的話它的回覆就不貼了，比這一步之前退步）：照樣進 spool、不帶 `dc_pane`、標 `dc_unplaced`，由機器人在認頻道的同一處（`unplaced()`，`handle()` 和 `waits()` 都問）判斷：**session id 等於頻道記的那個才是這個頻道的**（視窗還在時 fork 的 SessionStart 已經把頻道記的 id 換成它），其餘（預備行程、清單開的對話）不處理：不蓋 id、不貼、不留事件、不進 #audit，它問的問題交還終端機自己的選單（hook 收到 `{"pass": true}` 就不輸出）、計畫交還終端機的對話框，每個 session 在 `state/events-unplaced.log` 記一行（超過 200 KB 換成 `.1`）。路由那條路（`--global`、接上的窗格）對不上時照舊不進 spool：那邊沒有頻道 id 可以比，**已知限制**：接上的窗格被關掉後，被搬走的對話在背景跑完的那一輪不會貼。`CLAUDE_JOB_DIR` **只用來決定要不要多做這個檢查**：沒有它的無窗格事件一律照以前的路走；哪天 Claude Code 不再給這個變數，行為退回這一步之前（不會更糟）。那個窗格同時在路由表裡（開過又 `/attach` 的視窗）時這條路不報，由 `--global` 那條報。
    - **背景對話的清單畫面不打字**（同一步；真畫面樣本在接頭 `screens/<版本>/agents/`，兩版、120x50 和 80x24 各 18 種）：`screen.pane_state()` 多一種 `"agents"`，所以每一處「不是一般輸入框就不按鍵」（打字前、每次 Enter 前、`/btw`）都擋得到。清單照 Claude Code 自己畫的地方認（`agents_list()`）：框下面的狀態列有「enter to return／open／create」；或狀態列被截掉時，畫面最上面幾列有清單的標頭（Claude Code 標誌的第三列：「▝▝ ▝▝ N awaiting input · M working · K completed」；同樣的字出現在對話內容的一列不算）而且狀態列沒有一般對話的「(shift+tab to cycle)」「for agents」。框裡、清單各列的字（是對話內容）都不看。`may_type()`：清單的框裡有字（`"typed"`，使用者打到一半）→ 任何視窗都不按鍵、只說一句；框是空的 → 接上的窗格不按鍵、請使用者在終端機按 Esc；機器人開的對話和視窗按一次 Esc（`tmuxio.escape`，只在畫面還是空清單時），之後等到畫面是一般的輸入框才打字（最多 `LIST_LOOKS` 次；重畫到一半、沒有框的畫面不算），等不到就不送並說明按過一次 Esc。按了 ← 而工具還在跑（畫面多一列「● Backgrounding after the current tool finishes…」，整列相同而且狀態列顯示在忙才算，`moving_away()`）→ 等它搬完（最多 `MOVING_LOOKS` 次）照清單處理，等不到就不送並說明。頻道記著對話被搬走（`parked(st)`）而畫面標頭第三列是「@claude · 」（`list_started()`：清單開的對話；被搬走的那個只有資料夾）→ 不打字、請使用者回到原本的對話。**已知限制**：標頭捲出畫面後（對話一長、或 80x24）分不出窗格現在看的是原本的對話還是清單開的另一個，訊息會照常打進去；被搬走的對話本身是用 `--agent claude` 開的話會被當成另一個對話而擋下。80 欄的窗格在對話搬到背景後，狀態列變成「… ← for agents · esc to inter…」，`busy_shown()` 讀不到在忙（另記，不屬這一步）。
    - **路由檔的讀改寫沒有鎖**（`routecore.save()` 只有原子寫）：目前每台只有一個寫的人（本機是機器人，別台是 `dcremote` 的 bind／unbind），hook 只讀。之後誰要多加一個寫的人（例如讓 hook 記東西進去），得先替所有寫的人加鎖（主管 2026-10-14）。
    - 接上時在 `st["note_next"]` 放一段說明（在 Discord 的哪個頻道、不要用表格、用 `altention dc post <ID> --file` 傳檔案），跟著第一則訊息送進去：接上的對話是在機器人之外開的，沒有機器人的系統提示。
    - 輸入框上面那條橫線，對話有名字時會帶著名字（`──── 對話的名字 ─`），`screen.is_box_rule()`（`screen.box_span()` 用它找輸入框）要認得，否則 `has_prompt()` 以為開著面板，打字前會按 Esc（在 `claude attach` 的檢視器裡會把訊息弄丟）。

- `bot/ask.py`：Claude 的 AskUserQuestion 工具（在終端機會開選單，Discord 上沒人能操作）。`state/claude-settings.json` 另外為這個工具掛了 `dchook --ask`：它把題目寫成 `Ask` 事件後**等著**，`ask.py` 把每一題貼成一則訊息（選項是按鈕，複選或選項多是下拉選單，另有「其他…」開輸入框），全部答完後把答案寫到 `state/answers/<id>.json`，hook 讀到就以「允許 + 改寫工具輸入（加上 `answers`）」回給 Claude Code，工具直接帶著答案回傳，選單不會出現。只剩一題沒答時，頻道裡打的字直接當答案（`Asker.typed()`，`main.deliver()` 送進 tmux 之前先問它；計畫不適用）。按鈕靠 `custom_id`（`ask:<id>:<第幾題>:<選項>`）在 `on_interaction` 裡辨認，等待中的題目記在 `state/asks/`，所以機器人重啟後按鈕照樣有效。`!stop`、`!reset`、這一輪結束都會把還開著的題目標成已取消。plan mode 的「要不要照計畫執行」走同一套：`PermissionRequest`（matcher `ExitPlanMode`）掛 `dchook --plan`，貼出計畫和兩顆按鈕。核准時 hook 回 `{"behavior": "allow", "updatedInput": 原本的工具輸入}`，**少了 `updatedInput` 終端機的對話框不會關**；要修改就回 `deny` 加上使用者寫的話。用 `PreToolUse` 回 allow 沒有用，對話框照樣跳出來。

- **一輪是哪一輪、頁尾算誰的**（2.2e，#issues 27）：`Turn.pid` 記這一輪事件的 `prompt_id`；帶著別的 `prompt_id` 的輸入／工具／結束／失敗事件到了，還開著的那一輪就是沒有事件就結束的（Esc 中斷：Claude Code 不發事件），先收掉再處理（`another_turn()`），所以被中斷那一輪的工具次數和秒數不會算進下一輪的頁尾。`watch_busy()` 看到畫面三次沒在忙時只是「歇著」（`rest()`：不再顯示輸入中、收掉「處理中…」訊息、`Turn.quiet`），**不丟掉那一輪**：它可能卡在權限對話框幾分鐘後繼續，結束時頁尾照樣有工具次數和秒數（含等的時間）；窗格不在了才是真的結束。沒有 `prompt_id` 的版本：歇著之後使用者的下一句話算新的一輪。**一輪的結束等自己那一列（2.2f）**：Claude Code 先叫 Stop 的 hook、約 0.1 秒後才寫這一輪最後回覆的列（實量：真的 API 79 輪，dchook 的 `ts` 之後 0.083–0.107 秒；跟 hook 跑多久無關），而頁尾的 context 就是從那一列的 usage 讀的。以前 Stop 一到就處理：新對話第一輪沒有 context、之後每一輪顯示的是上一輪的。現在接頭的 `hooks.awaits()` 對 `Stop` 也回「先留著」，直到對話檔裡從讀到的位置往後出現這一輪的 `hooks.last_reply()` 列（assistant、不是側鏈、帶 usage、`stop_reason` 是 `end_turn`；同一個回覆每個內容塊各一列、同時寫、都帶同樣的 usage，看到任何一列就夠；被截斷（max_tokens）或被拒（refusal）的列不算，Claude Code 自己會再問；`stop_reason` 是別的（例如停在 stop sequence 的正常回覆）時，文字等於事件的 `last_assistant_message` 也算；API 錯誤的列（`isApiErrorMessage`）不算）；最多等 `END_HOLD_SECS` 0.5 秒（從事件的 `ts` 算，積著沒人看的事件不等），到了照有的做並計數（`hooks.ends_late()`；只計「等過而沒等到」的：第一次被看到時已經超過上限 `LATE_WITHIN` 2 秒以上的舊事件不計；機器人第一次在 supervisor.out 留一行、次數寫在 `state/turn-ends-late.json`，doctor 還沒讀）。**不等的**：沒有 `last_assistant_message` 或它是空字串的 Stop（模型回空，不會有那一列）、`StopFailure`（它的列也晚 0.1 秒，但失敗訊息不顯示 context）、子代理的事件、沒有 `prompt_id` 或 `ts` 的、還沒見過的對話檔。是哪一輪的列：這一輪自己第一列（`promptId` 等於事件的 `prompt_id`）之後的，找不到第一列時比對文字（事件的 `last_assistant_message` 只有回覆**最後一個文字塊**、而且去了頭尾空白）。留著的方式跟 1.6b 的工具列相同（本機留在 spool、同頻道後面的排在後面、別的頻道照走；別台是 `dcremote` 的 relay 用同一個函式，有東西留著時 stream 0.1 秒後再看）；`INTERIM` 關掉時工具列不等、結束仍然等（`awaits(calls=False)`）。量到的事實和樣本在 `altention/tests/connectors/claude_code/turn_ends/`。

## 願望放哪裡
使用者許願時，先決定改動落在哪裡，再動手。目標是使用者說一句話就有新功能，同時公開的核心不會越來越大、越來越個人。

1. **調整既有行為、修問題**：直接改核心（`dcbot/`），照下面的修改流程部署。這是大多數的願望，不要為了「乾淨」硬繞成插件。
2. **新的獨立功能**（自己的訊息、按鈕、指令、排程，不必動機器人的內部）：做成本地插件，放在實例的 `plugins/`，程式和個人資料可以混寫；好用了再整理成公開插件。
   - 插件執行層和擴充點還沒上線之前（2026-10-11 還沒：`ops/plugins.py` 已經有了，但它和 `altention/plugin.py` 只做內建插件的宣告、比對和回報；實例的 `plugins/` 還沒有東西會去讀，擴充點也還不存在。上線時這一句會改掉，在那之前不要照第 2 點做本地插件），這類功能先照第 1 點做進核心，並守第 3、4 點。
   - 插件的程式不載入機器人行程：機器人在事件發生時執行插件宣告的指令。需要機器人內部資料（tmux 畫面、對話紀錄）的功能做不成插件，照第 1 點做。
3. **不是人人適用的核心改動**（只合這位使用者的習慣）：做成實例設定的開關（`altention.config.setting("core.…", 預設值)`），**預設維持原行為**。拿不準是不是人人適用就做成開關。
4. **個人的值不進引擎**：機器名、帳號、頻道名和 ID、私人網址、路徑一律從 `altention.config` 或實例設定讀；測試用假值。部署時個資掃描的結果會印在 `deploy.sh` 的輸出裡，它不擋部署，但看到警告就在同一輪改掉（發佈時才擋，累積下來發佈就做不了）。
5. 介面文字（貼給使用者看的字）新寫的放 `altention/text.py`。

## 修改流程（一定要照做）
1. 改程式。新功能盡量做成獨立模組或 `tools/` 下的小工具，不要把 `main.py` 越塞越大。
2. 為新功能補測試（`tests/`），至少確保能 import、純邏輯有單元測試。
   - **要假的 tmux 窗格就用 `tests/fakepane.py`，不要自己 `mock.patch.object(tmuxio, …)`**（2026-10-11）：`with fakepane.use(假物件或 raw_screen=…, keys=…):`；單一替換或常數用 `fakepane.replace("名字", …)`。它只在一個地方記每個函式在哪個模組（`WHERE`），函式搬家改那一行；替換對象不存在、或只是從別處轉手的，直接報錯；`use()` 期間任何程式想開真的 `tmux`／`ssh` 會丟 `fakepane.Reached`（不是 `Exception`，橋接的 `except Exception` 吞不掉）。少了這個，替換沒生效的測試會默默去碰正在跑的機器人的 tmux。
   - 動到「送出 → 打字 → hook 事件 → 貼回覆」這條路，`tests/test_whole_turn.py` 要過：它用真的 `tools/dchook`、真實格式的對話檔（`tests/transcript.py`），本機（spool → `pump_once`）和別台（`dcremote` 的 `relay` → `stream`）各跑一輪，看收件的 👀、中途的話、回覆和頁尾、📋 的位置。開對話那段（`ensure`／`ensure_home`／`wait_ready`）在 `tests/test_open_session.py`。
3. 使用者用得到的功能有變（新指令、行為改變、新的限制）就更新 `docs/usage.md`（完整說明，給 agent 讀：使用者在任何頻道問用法時，Claude 照它回答），有新功能或功能的叫法變了才也改 `GUIDE.md`。`GUIDE.md` 是說明頻道的內容（預設 `#guide`，名字可以用實例 plugins.json 的 `dcbot.channels.guide` 改），是精簡的規格書：第一行請使用者有不懂的直接問 agent，接著每個功能一行（名字、一句話、怎麼叫），不寫細節和已知限制。用 Discord 看得懂的格式（標題、清單、粗體可以，表格不行）；每個 `## ` 段落是一則訊息，別超過 1900 字。`GUIDE.md` 和 `docs/usage.md` 是範本：機器名、頻道名這類因安裝而異的字寫成 `{{變數}}`（有哪些變數、各從實例的哪裡來，見 `GUIDE.variables.md`），不要直接寫出來；「其他頻道」那一段的內容在實例裡。改完用 `tools/dcctl guide --check` 看展開後的樣子。
4. 執行 `./deploy.sh "commit 訊息（英文）" "給使用者看的更新說明（中文，兩三句）"`：語法檢查 → 測試 → commit（只有 `dcbot/`，加上第三個參數之後列出的路徑，例如 `../ops`；同一個工作樹裡別的頻道改到一半的東西不會被帶出去，有的話會列出來）→ pull（衝突就取消 rebase、不 push）→ push → 把 `GUIDE.md` 同步到說明頻道（原地編輯；有第二個參數就多貼一則更新紀錄，只留最近 5 則）→ 有改到 `dcbot/` 才重啟。純內部修改可以不給第二個參數。
   - **不等機器人重啟就會被執行的東西，一律 `./deploy.sh --commit <審過的 hash> "訊息" ["更新說明"]`**（2026-10-09 起）：`altention/`、`chatlog/`、`progress/`、`bin/`、`ops/`、`tools/`、`dcbot/tools/`、`deploy.sh`、`deploy_candidate.py`，以及 `dcbot/tools/*` 會 import 的 bot 模組（`deploy_candidate.live_modules()` 從 import 算出來：`events`、`tmuxio`、`config`、`remote`…（接頭在 `altention/` 底下，那邊的檔一律不算可以原地改），不是照資料夾分）。在別的 worktree 做好、提交、送審；`--commit` 會在 `.git/altention-deploy/candidate`（暫時的 worktree）做出候選 commit（HEAD 加上那個 hash 對它的基底改的檔，印出「patch-id 相同」），所有檢查都在那裡跑，全過才拿鎖把正式樹快轉過去；之前正式樹一個位元組都不動，cron 和 hook 跑的還是舊程式。基底之後 main 上有別的 commit 動到同樣的檔、或正式樹裡那些檔有沒提交的修改，就停。失敗時印「正式樹沒有被動過」（比對 HEAD、git status、那些檔的內容），候選和測試輸出留在 `.git/altention-deploy/`（下次部署清掉）；成功就刪掉。`dchook --update` 在換過去之後才跑。main 到那個 hash 之間的每個 commit 都要列出來（疊了幾個就給幾個 `--commit`，每個都審過；沒列到的會被擋，沒審過的不能跟著上線）。做候選前和換上去前都會 fetch：origin 比這台的 main 新就停，先 `bin/home-pull` 接進來再部署（不然換上去之後才接，推出去的是沒驗過的樹）。一次只有一個 `--commit`（`.git/altention-deploy.lock`，第二個直接拒絕並說誰在部署）。**後續的修正從現在的 main 開新的 worktree**，不要疊在已經部署過的那個審過的 hash 上：main 上的是候選 commit，不是那個 hash，疊上去的會因為「基底之後 main 動過同樣的檔」被擋。
   - 原地改再 `./deploy.sh "訊息"` 只給機器人重啟前沒有人會執行的檔（`dcbot/bot/` 裡 tools 不會 import 的模組、測試、文件、`requirements.txt`、`supervisor.py`）；改到別的會被拒絕並列出來。
   注意：`dcbot/` 以外的修改（`altention/`、`ops/`、`bin/`、內建插件、skill）會被所有機器拉去用，自動回滾也救不回來；改之前先跟使用者確認。
5. 回覆使用者改了什麼。重啟後，機器人會在這個頻道回報新版本有沒有上線；失敗會自動退回並說明。

在 tmux 模式下，`deploy.sh` 之後機器人會馬上重啟，你這一輪不受影響，回覆會由新版本貼出。改到 `tmux_bridge.py`／`tmuxio.py`／`dchook` 時，除了單元測試，請另外用假的頻道物件加真的 Claude 跑一次（開一個不同名字的 tmux socket，不要動 `dcbot` 這個 socket）。

不要直接 `kill` 自己或手動重啟；不要 `git push --force`；不要改寫 git 歷史。

## 慣例
- 回覆使用者用實例設定的語言（`core.language`，預設繁體中文）、精簡，先講結論。使用者另有偏好的話寫在實例附錄。
- 破壞性動作（刪頻道、刪檔、強制推送）先問，得到明確同意才做。`dcctl delete` 需要 `--yes`。
- 只用標準函式庫或 `requirements.txt` 裡的套件；要加新套件就寫進 `requirements.txt`，`deploy.sh` 會自動安裝。

## 環境
- 頻道預設的工作目錄：新安裝是實例資料夾（讀得到知識和記憶，又不會在引擎裡留下修改）；改機器人自己時，檔案在引擎的 `dcbot/` 底下。這個安裝實際用哪個資料夾，見實例附錄。
- 機器：`altention.config.machines()` 給機器清單，`bot_machine()` 給機器人在哪台（角色 `dcbot`）。其他機器用 SSH 連線，別名也在清單裡。沒有清單就是只有這一台。
- 裝了哪些插件、各自的資料在哪（例如對話紀錄、專案進度）：見實例設定和實例附錄。別的插件的資料一律唯讀。
