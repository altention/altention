# 頻道和對話的生命週期

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- 頻道被刪（`on_guild_channel_delete`）：清掉頻道狀態和路由，但不關 Claude（可能有進行中的工作），在 `#audit` 留下它在哪裡。它還開著的提問和計畫當場放掉（`Asker.gone()`：提問回絕並請它在終端機用文字問、計畫交回終端機自己的對話框；訊息跟著頻道沒了所以不編輯）；之後那個對話再提問，`handle()` 看到**頻道狀態裡已經沒有它**（確定被刪）也當場回同樣的結果（`ask.gone_result()`），不讓 hook 等到上限（#issues 21，2.2e）。**拿不到頻道但狀態還在**（Discord 重連中、頻道還沒進快取）不是被刪：那個頻道的事件留在記憶體裡照順序排著（`keep()`），頻道拿得到了再處理（`release_kept()` 每一輪看一次、**開一個獨立的工作** `release()` 去放；那個頻道到全部放完才從 `kept` 拿掉，放的期間新到的事件（含別台 stream 那個工作來的）排到隊尾，不交錯、同一個頻道不會同時兩個 `handle`；最多留 `KEPT_SECS` 600 秒、每個頻道 `KEPT_MAX` 500 個，超過就丟，supervisor.out 的行同一個頻道只印一次；提問不回絕）。超過 600 秒還拿不到、狀態還在的頻道記在 `away`，寫進**自己的檔** `state/channels-unreachable.json`（頻道 id、從什麼時候起、丟了幾個事件、原因；`note_away()`）。**不放進 `ownerless-sessions.json`**：那份清單在 doctor 的建議是「不要了就關掉」，而這種頻道可能還在用（Discord 連續十分鐘拿不到時正在用的頻道也會被列）：不確定的東西不能放進「可以關」的清單（主管 2026-10-13）。doctor 還沒有讀這個檔（之後在 ops/ 加一項，字要寫成「Discord 拿不到這個頻道」）。**提問關掉之後要交給別台 hook 的結果只有一條路**（`Asker.hand()`：刪頻道的 `gone()`、一輪結束的 `cancel()`、回收沒有頻道的對話 `reap_ownerless()` 都走它）：本機的當場寫檔；別台的**不在原地等**，紀錄留著並記上要送的結果（`owed` 欄位；這種紀錄對 `load()`／`waiting()` 來說已經不是開著的提問），由**每台一個的獨立工作** `refuse_again()` 送（記上的當下就起工作）（30 秒起、每次加倍、上限 10 分鐘；有指令送得到那台或它的 stream 回來時立刻試），`pump_once()` 只負責起這個工作（`start_resends()`）。**通則（主管 2026-10-13）：`pump_once()` 和它叫的 tick 裡不可以 await 任何會碰別台或網路（Discord 的 REST 以外）的東西；要做就開獨立的工作**（#code-review 量到：在這一圈裡等一台連不上的機器，本機所有頻道的事件都跟著停）。
- 閒置回收（`tmux_bridge.reap()`，每 10 分鐘）：頻道自己的對話閒置超過 `IDLE_HOURS`（預設 12）就關掉，下一則訊息自動接回。**頻道已經不在的對話**（`reap_ownerless()`，2026-10-11，#issues 10）照「停掉東西只靠讀得到而且明確的事實；不確定就不關、列給人看」處理。全部成立才關：每個窗格都在跑 Claude Code，而且行程的環境（`/proc/<pid>/environ`，`tmuxio.started_for`）裡 `DCBOT_ROOT` 是這個機器人、`DCBOT_CHANNEL` 是一個頻道 id（**不看 session 的名字**）；那個頻道沒有狀態、Discord 上也沒有；沒有任何頻道狀態用任何一種寫法記著這個 session（`tmux_bridge.sessions_named`：`tmux`、`home.session`、`pane_session`、封存紀錄裡的兩個；`tests/test_reap.py` 的表列出每個寫入點，新增寫法要一起加）；`IDLE_HOURS` 沒有畫面變動（tmux 的 `window_activity`；`session_activity` 沒人接上時停在建立時間，不能用）、沒人 attach、畫面上沒有一輪在跑；**Claude Code 行程底下沒有子行程**（`tmuxio.children`：背景指令是它底下的 shell，畫面看起來是閒著的，只看畫面會把訓練關掉；閒著的 Claude Code 底下什麼都沒有）。頻道狀態整個是空的（狀態檔讀不出來時機器人就是這樣啟動）一個都不關。Discord 的頻道清單還拿不到時（狀態裡的頻道沒有一個 `get_channel` 得到：剛啟動、斷線）也整輪不關、不改清單：那時「Discord 上沒有那個頻道」其實是「還不知道」。關之前 #audit 記一行，它那個頻道 id 的提問一併取消。有一輪在跑、底下有行程、或讀不到的，不關，寫進 `state/ownerless-sessions.json`，doctor 的 `dcbot.ownerless-sessions` 會 warn 並列出名字、閒置多久、原因，由人決定。對話內容都還在磁碟上（`claude --resume`）。
- **接回失敗留證據**（C-161，2026-11-04）：機器人自己 server 上的對話用 `tmuxio.start()` 開，同一個 tmux 呼叫裡設 `remain-on-exit on`（不加 `-t`，指剛開的視窗），所以 Claude 一啟動就結束也看得到為什麼。開起來（`kept()`）就 `tmuxio.settled()` 關掉，之後跟以前一樣隨 Claude 結束。沒開起來：`failed()` 用 `tmuxio.ended()` 讀一次結束碼、訊號和最後的畫面（`capture-pane -S -<高度>`：tmux 3.4 寫「Pane is dead」時會把第一行捲進歷史），然後馬上關掉那個死掉的 session；接回失敗那一次讀到的，遮罩後接在「接不回原本的對話」後面貼出來。`alive()` 把窗格已經死掉的 session 當成沒在跑（先 `has-session` 再問 `pane_dead`：tmux 3.4 對不存在的目標問 display-message，會拿目前 session 的值回答）；`start()` 遇到同名、已經死掉的舊 session（機器人中途重啟留下的）會先關掉。只有機器人自己 server 上的對話這樣做；開在使用者 tmux 或別台的視窗（`ensure_home()`）沒有。同時，機器人開的每個對話（本機和別台）都帶 `RESUME_ENV`：`CLAUDE_CODE_RESUME_THRESHOLD_MINUTES`、`CLAUDE_CODE_RESUME_TOKEN_THRESHOLD` 設成很大的數字，2.1.318 接回很舊又很大的對話時就不會問要不要從摘要接回（程式裡讀成整數，11-04 實量）。不改使用者自己的設定。那個框沒看過真的畫面，所以沒寫靠字詞的偵測（manager 11-04）。它有三個有編號的選項，`startup_choice()` 不認得（它只認兩個沒編號的 Yes／No）：真的跳出來時，在 SessionStart 之前就是等到 START_SECS 算沒開起來，之後就是送訊息時說「畫面不是一般的輸入框」，都不會替使用者按。
- **「結束了」只在真的結束時說**（2.3，#issues 20）：頻道裡的「ℹ️ 這個頻道的 Claude 結束了（tmux 視窗被關掉了？）…」和「ℹ️ 這個對話在終端機那邊結束了…」只在種類是 `session_ended` 時貼；`session_leaving`（`/clear`、`/resume` 換對話時舊對話的 SessionEnd：同一個 Claude Code 還在跑，接著會有 SessionStart）什麼都不貼。以前在機器人開的視窗裡 `/resume` 會被說成結束了。
- **別台窗格 `/resume` 之後也貼那個對話的紀錄**（2.4c，#issues 31；在這之前只有本機的貼）：事件（`session_changed`、原因 resume、對話換了）帶著 `transcript_path`，機器人起一個自己的工作 `history.show_remote()`：`dcremote history FILE [SESSION]`（唯讀；路徑解開（realpath）後不在那台 Claude Code 自己 projects 資料夾底下、或不是 .jsonl 的不讀；projects 裡指到另一個自己對話檔的連結會讀，規則和結束碼同 `turn`／`part`：3 不給、4 讀不出來、檔不在回 null）拿回 `{session_id, turns}`，跟 `/attach` 的 backfill 同一個形狀、同一份組字（`sessions.backfilled()` → `bot.backfill()`）；頻道貼過這個對話就只貼最後三輪。最多等 20 秒；那台連不上／dcremote 還是舊的（結束碼 1 **而且** stderr 有「不認得」）／dcremote 自己跑不起來（結束碼 1 的其他情況：把結束碼和 stderr `history: …`。已知限制：那台的 Claude Code 用自訂 `CLAUDE_CONFIG_DIR` 時 dcremote 看的是預設位置 → 結束碼 3（跟 📋 的 `turn` 同一個限制，GUIDE 有寫）。**不在那台的 stream 處理事件的地方等**（`handle()` 只 `ensure_future`）。接上的窗格（本機、別台）`!resume`／`altention dc post --resume`／`--history` 照舊不給。**機器人開在別台的 home 視窗的 `!resume`**（#issues 35；在這之前查的是這台同一個路徑的資料夾）：`bot.resume()` 看 `sessions.elsewhere(st)`，對話在別台就問那台：`dcremote sessions FOLDER [REF]`（唯讀；不帶 REF＝`cc_sessions.recent(FOLDER, 8)`，帶 REF＝`find()`；每筆多一個對話檔的 `path`，title／first／last 截到清單會顯示的長度 80／40／50；FOLDER 不是那台存在的資料夾 → 3、讀不出來 → 4）。回來的每一筆先對形狀（`history.a_session()`）才用；清單、編號、「已在這個對話上」「被別的頻道使用」都是本機那一套（`sessions.listing()`／`pick()`）；選定後關視窗、換 session_id、起 `history.show_remote()`（路徑用那台回的，那台讀之前自己再驗一次）。拿不到 → 「這個頻道的對話在 <機器> 上，…，所以列不出那台的對話、也沒有換對話。」（分法同 `history.failed()`），頻道不動。別台頻道的 REF 絕不拿去查這台的資料夾（清單裡沒有、又不到 8 個字 → 找不到）。**機器人自己關掉的別台視窗，之後它的結束事件不說話**（同一步；在這之前 `!resume`、`!reset`、`!cwd`、`!mode`、閒置回收在別台 home 視窗都會多一則「這個頻道的 `dc_routed`（事件格式多兩個欄位；relay 原樣帶過來）；`from_elsewhere()` 對「`dc_routed` 而且頻道有 home」的事件照本機同一段比（別台的比 host＋socket＋窗格編號；`close()` 已經把頻道的 pane 拿掉 → 不是這個頻道現在的視窗 → `let_go()`）。接上的窗格（沒有 home）的路由事件照舊不判；別台的 dchook id 等於被關的那個**、而且**是 SessionEnd** → 別處來的（2.6c 收窄：被關的視窗之後只會來這一種，#code-review-2 量 48 次關掉跑到一半的視窗都是；其他種類的事件一律照常處理，任何情況都不吞掉一輪）。其他都照常處理（寧可多一則「結束了」，不可吞掉一輪）：別的 id（新視窗的；紀錄留著，它只比舊 id）、事件沒帶 id（不判）、舊 id 的 SessionStart（新視窗在同一個窗格接回同一個對話，從此分不出來，紀錄拿掉）。不能只看窗格編號（關掉 tmux server 最後一個視窗後 server 結束，新視窗的編號常常又是同一個），也不能等新視窗的 SessionStart（別台的可能在路由寫好前就發出、永遠不進 spool：ddf02aa 因此整輪不貼）：所以視窗確認開好時 `opened()` 也把「同窗格、同對話」的紀錄拿掉。已知限制：新視窗在同一個編號接回同一個對話之後，舊視窗的結束才到（本機；別台路由換了 pid 之後舊視窗的事件進不來），照舊說那一則；舊視窗裡有機器人沒看到的換對話，它的結束也照舊說。同一個頻道一次只跑一個 `!resume`（`bot.resuming`，finally 清掉）：等別台的那段時間再下一次，回「這個頻道正在接回另一個對話，等它完成再下一次 `!resume`。」。`altention dc post --history` 對這種頻道：先 `sessions FOLDER <頻道現在的 id>` 拿路徑，再 `show_remote(force=True)`。`/resume` 選單的自動完成對這種頻道回空清單（Discord 要 3 秒內回，不現場問別台、也不做快取）。
- `bot/sessions.py`：`!resume` 用。列出工作目錄在 `~/.claude/projects/` 底下的對話紀錄（只讀），每個頻道用過的對話記在 `channels.json` 的 `history`。`!reset`、`/clear` 都會把舊對話記進去，所以開新對話不是不可逆的。
