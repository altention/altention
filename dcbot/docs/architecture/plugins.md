# 插件的按鈕和改寫

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/rewrite.py`（C-71b）：插件在 plugin.json 宣告 `rewrite`（command、timeout ≤60、when；格式寫在模組說明），機器人那台 placement 是 on、order 最小的那一個才用（`choose()` 在執行緒裡讀，啟動和每分鐘一次）。Stop 時回覆對得上 `when` 就寫進頻道狀態 `rewriting`、`self.rewriting` 加上這個頻道、開一個獨立的工作 `rewrite_and_post()`：跑插件（自己的 process group，逾時整組砍掉），回來的訊息照順序貼（`post_reply()`：文字＋多張圖、頁尾接在最後一則、📂／📋／#audit 照舊記在最後一則），失敗、逾時、看不懂或「一則沒圖」就照 C-71a（`plain_reply()`）。等的期間這個頻道的本機事件留在 spool（`waits()`）、別台的 `keep(quiet=True)`，貼完 `release()`；但機器人自己打進去、正在等回條的那則的 UserPromptSubmit（`receipt_meanwhile()`：對得上 `rt.pending`／`rt.late`）照常處理，不然 submit 等不到就說「可能沒送進」、晚到的回條又被當成終端機輸入（#code-review-2 預演擋 f2ee5d3）；不是機器人打的 input 會貼「⌨️ 終端機那邊輸入」，照樣等。改寫子程序的 process group 和它的開始時間（`/proc/<pid>/stat`）記在 `rewriting` 的 `pgid`、`pgid_start`，重啟時 `posted_left()` 先 `rewrite.stop_left()`：開始時間對得上才 killpg（macOS 沒有 /proc，不殺）；超過 `SHOW_AFTER` 5 秒貼一行「⏳ 整理排版中…」，貼完刪掉。機器人重啟時還在 `rewriting` 的照 C-71a 貼（`posted_left()`）；`busy_with_work()` 算進去。圖只收 `<state>/rewrite/<token>-*.png`，貼完刪，殘留的 10 分鐘雜事清一天以上的。
- `bot/activity.py`（C-116，貼檔案的按鈕）：`altention dc post --file` 每個檔案帶 `where`（`{machine, path}`：機器清單的名字、絕對路徑；超過 2048 bytes 不帶），`posts.py` 送附件前問 `launcher.for_files()`：宣告 `opens_files` 而且 `uses` 寫 `activity.pages` ≥2 的頁，每個檔案每頁一顆（`file_button`，沒有用 title；多個檔案接「：檔名」），一則最多 `FILE_BUTTONS` 5 顆，按鈕走下面同一套 token／intent；EMBEDDED 確定是 false、讀不到宣告時不附，附件照貼。
- `bot/activity.py`（C-54a）：插件 Activity 頁的「打開」按鈕。插件在 plugin.json 宣告 `activity.pages[]`（`id`、`title`、`access`：`owner` 預設／`guild`；`plugin.py` 檢查）。`altention dc post <頻道> --activity <插件>/<頁> [--arg k=v…]` → `Posts.activity()`：頁要是開著的插件宣告過的（`pages_now()`：在執行緒裡讀、最多 `READ_SECS` 2 秒），整段貼出（別的頻道寄的是卡片；長的照一般 post 分則），按鈕在最後一則，不交給 Claude；沒有那頁就 #audit 一行、告訴寄件的 Claude。按鈕的 `custom_id` 只有 `act:<secrets.token_hex(16)>`，開什麼記在頻道狀態 `activity`（每頻道 50 顆、7 天），所以重啟後照樣能按、客戶端送來的 custom_id 決定不了開哪一頁。按下去：token 對不上、或記的時間超過 7 天（沒記時間也算）就說失效；**當場重讀宣告**、照現在的 access 判斷（owner 頁只有擁有者、guild 頁要在這個伺服器；讀不到、超過 2 秒、頁不在都不開）；寫 intent 到 `~/.local/state/altention/activity/<插件>.json`（呼叫當下從 HOME 算，600，暫存檔＋rename，留 20 筆、10 分鐘；欄位 user、channel、guild、page、args、access、at；插件後端用驗過的使用者 ID＋頻道找最新一筆，只讀不寫）再回 LAUNCH_ACTIVITY（discord.py ≥2.6），Activities 開了沒（application 的 EMBEDDED flag）在按之前就要知道：沒開時 Discord 回 400（50234），之後這次互動就失效，第二次回應是 404（#code-review-2 在正式 App 上量到）。`embedded` 先拿 READY 給的 flags，`watch()`（獨立的工作，每 10 分鐘 `application_info()`）更新，讀失敗就留著原本知道的；按下去只看它：確定沒開就第一次回應說去 #setup 裝完、不寫 intent；開了或不知道就照常送 LAUNCH_ACTIVITY，還是被拒就只記一行 log、不送第二次，50234 時把它標成沒開。
- `bot/secretbox.py`（C-77 G3b）：插件金鑰的「填入」按鈕。`altention dc post <頻道> --secret <插件>/<名字>` → `Posts.secret()` → `Secrets.post()`：名字要是這台插件 `secrets[]` 宣告過的（`secret_store.declared()`，在執行緒裡讀、最多 `READ_SECS` 2 秒），按鈕和輸入框上的字是宣告的 `label`；沒宣告就不貼，#audit 一行、告訴寄件的 Claude。按鈕 `sec:<token>`、輸入框 `secm:<token>`（`token_hex(16)`），是哪個金鑰記在頻道狀態 `secret_boxes`（每頻道 `KEEP` 20 顆、7 天）。輸入框顯示後馬上 `stop()`，不留在 discord.py 自己的 store，它的回答跟按鈕一樣由 `on_interaction` 照 custom_id 收（重啟後也收得到；兩邊都收會回應兩次）。按鈕和輸入框都只有擁有者（各自再查一次）。值由 `store()` 從 stdin 交給核心 `altention/secret_store.py set <插件> <名字> --stdin --via discord`（`STORE_SECS` 90 秒，逾時整個砍掉），機器人不寫檔、不留副本；核心印的幾行（存好了／沒有存，存好了時還有這個插件在哪幾台用、要送過去請 Claude 跑 `setup.py secret-send`；機器人不自己送，manager 2026-10-24）只回給按的人，#audit 由核心記；存好了（結束碼 0）就把那則訊息的按鈕改成「✅ 已填入 …（再按可以換）」（`button(filled=True)`，同一個 token，照樣能再按；notice-design §7 第 5 項）。**值絕不進 log、狀態、訊息、例外的字**：`on_interaction` 出錯只印種類，不印 traceback（輸入框的回答在堆疊的資料裡）；失敗只說種類或結束碼。Discord 的輸入框沒有密碼型，貼出的訊息每次都附一行說明（manager 裁示）。字在 `messages.SECRET`（組 `secret`）。
