# Discord 用戶端和兩種模式

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/main.py`：Discord 用戶端。只聽擁有者（OWNER_ID），每個頻道對應一個持續的 Claude Code 對話（`state/channels.json`）。內建指令 `!status !reset !resume !recap !commands !attach !detach !stop !cwd !mode !screen !key !restart !rollback` 不經過 Claude，是壞掉時的救命繩，**不要拿掉**。
- 每個頻道有兩種模式（`!mode`，預設 `tmux`）：
  - **tmux 模式**（`bot/tmux_bridge.py`）：Claude Code 以互動模式活在 tmux 裡（機器人自己的 tmux server：`tmux -L dcbot ls`、`tmux -L dcbot attach -t <名稱>`）。行程不屬於機器人，所以機器人重啟／部署不會打斷對話，背景工作跨輪存活，處理中途可以補充訊息。
    - **窗格物件**（`tmuxio.Pane`，3b 2.4a）：開對話的那幾處經過它讀畫面、按鍵、問還在不在、收掉自己開的；它不做決定，每個方法就是 `tmuxio` 同名的函式（呼叫時才查，所以 `fakepane` 的替換照樣有效）。測試要直接給一個窗格時用 `fakepane.Pane(fake, 目標)`。打字、選單、btw 還沒經過它（2.7a）。
    - **開對話**（3b 2.4b）：指令列和設定檔在接頭 `launch.py`（旗標的名字只在那裡；`launch.permissions()` 是合法的權限模式，照 2.1.296 的 `--help`）。`TmuxBridge.open()` 是唯一的一份迴圈（先試接回、不行開新的、等好、失敗收掉），三種頻道差的只有它拿到的三個小函式（怎麼開、開成之後記什麼、沒開成怎麼收）。**模型和權限**：頻道狀態的 `model`／`permission` → 這個安裝的設定 `dcbot.default_model`／`dcbot.default_permission`（`plugins.json`）→ 模型用現在的值（`config.MODEL`）；**權限模式沒有預設**（C-121，2026-11-03：以前最後退到 bypass，全部放行）：頻道和安裝都沒設就不開對話，頻道照 `tmux_bridge.UNSET` 說要設哪個值、怎麼設。舊安裝沒寫過這個值的，更新後第一次 reconcile（`ops/setup.py` 的 `write_permission()`）把它原本實際在用的 bypassPermissions 明寫進 plugins.json（行為不變，#audit、實例 commit、#update 各說一次），再在 #setup 用按鈕問要不要改。tmux 和 print 模式都只從 `tmux_bridge.permission_of()` 拿值。權限值不合法、或讀不到安裝的設定：**不開對話**並在頻道說明（讀不到的那句說是哪個檔、修好再傳一則就會開）（不退回預設值：預設是全部放行）；模型讀不到設定時用現在的值。不合法時的那句話說是誰的值（頻道的，或安裝設定 `plugins.json` 的 `dcbot.default_*`）；模型的值不是文字也不開。設定檔讀得出來時當場讀（訊息到開視窗之間不讓別的事件插進來）；讀不出來時才丟到執行緒（引擎讀到壞檔第一次會等 0.4 秒），不在事件迴圈裡等。**print 模式的頻道**：權限模式照上面（C-121），模型仍寫死 `config.MODEL`（記給 2.9）。測試：沒有自己實例的測試，`tests/fakepane.py` 讓安裝設定帶 `dcbot.default_permission`（每個安裝都有寫），測「沒設不開」的測試自己給空的設定。開不起來的每一種原因是 `NotOpened`（`BridgeError` 的子類別）：`why` 代號＋`data`，字照舊（2.6 之後用代號）。`state/claude-settings.json` 內容沒變就不重寫。測試：用假窗格的測試一律不讀真的安裝設定（`fakepane` 設 `ALT_INSTANCE=-`）。
    - 輸入：`bot/tmuxio.py` 用 `send-keys -l` 逐行打字（行間 Alt+Enter），再按 Enter。**不要改成貼上**：長的貼上會被包成 `<pasted_content>`。
    - 輸出：不抓畫面。`state/claude-settings.json`（啟動時產生，只套用在機器人開的對話；開視窗時用的是它加上附件資料夾的副本 `claude-settings.<12 碼>.json`，`tools/dchook` 的 `bot_window()` 兩種都認）掛了 hooks，由 `tools/dchook` 把每個事件寫成一個檔案放進 `state/events/`，`tmux_bridge.pump()` 讀出來貼到 Discord。`UserPromptSubmit`＝訊息送達（加 👀）、`PreToolUse`＝進度、`Stop`＝貼出最後一則回覆。進度（引言、「處理中」、📤）不在 pump 裡送：pump 只把它排進那個頻道的佇列（`bot/lanes.py`），每個 Discord 請求最多等 `LANE_SECS`；那個頻道的回覆、提問等事件在佇列送完前留在 spool（`lane_waits()`），其他頻道照走（11-10：一個 Discord 請求卡住 135 秒，整個 spool 跟著等）。
    - 中途的話：`Stop` 只帶最後一則文字。Claude 在工具呼叫之前說的話要從對話紀錄（事件裡的 `transcript_path`）讀：每個 `PreToolUse` 和 `Stop` 時用接頭的 `transcript.new_texts()` 讀出上次之後新增的文字，以引用樣式（`>>> `）貼出。每輪開始時把讀取位置移到檔尾，並略過跟最後回覆相同的文字，避免重複貼。設定 `INTERIM=0` 可關掉。
    - 失敗：API 出錯時沒有 `Stop`，而是 `StopFailure`（`error`：rate_limit、authentication_failed、billing_error、invalid_request、server_error、max_output_tokens、unknown；錯誤訊息在 `last_assistant_message`）。2.1.289 實測互動模式會觸發。`TmuxBridge.failed()` 貼出原因和「再試一次」按鈕（`retry:<頻道>`，送一句 `RETRY`）。
    - 通知：中途的話、進度訊息、⌨️／📤／📨 都 `silent=True`；正式回覆、提問、計畫、選單、失敗會響。**@ 擁有者只經過 `bot/calls.py`（C-103）**；機器人的 `discord.Client` 預設 `AllowedMentions.none()`（`main.client_options()`，訊息檢討 P0-1），所以回覆、卡片、Claude 寫的 `<@…>`、`@everyone` 都不 @ 人，只有 `calls.py` 送出時明寫 `allowed()`（只放擁有者）才會 @：要擁有者動手的事（按鈕提問、計畫、權限和其他選單、來回上限、要處理的中斷、送不出去的啟動失敗、最後回覆第一行是 `messages.DISCUSS_MARK`）各 @ 一次：一行獨立的訊息，目的在前、`<@擁有者>` 在最後，用「回覆」掛在那則下面；key 記在頻道狀態 `calls`（重啟後不重複），那件事結束時 `call_done()` 把那行改成結尾 ✅（編輯不會響）。整個安裝卡住的事（用量上限、某台登入失效、別台串流斷超過 `MACHINE_DOWN_SECS`，而且斷的那一刻那台有頻道在跑一輪或有訊息在等它；那台的頻道都閒著（常關機的 mac）就只在 #audit 記一行，manager 2026-11-03；Claude Code 不自己等的用量上限是 `blocked: api_error` 帶 `why: rate_limit`，`blocked.usage()` 兩種都算）用 `calls.system()` 在預設通知頻道只 @ 一次、列出受影響的頻道（`state/calls-system.json` 記這一次），結束時 `calls.over()` 補一行不 @ 的「恢復了」，下一次再 @。機器人停著時的事（一直重啟：`CRASH_COUNT` 次在 `CRASH_WINDOW` 內、中間沒穩定跑滿 `STABLE_SECS`；新版退回）由 supervisor 自己用 `dcctl send @notify --mentions` 直接送 Discord。寄件頻道的 ⏸️ 那行 `silent`，同一件事只響一次。字在 `messages.CALLS`。跑多久不再是 @ 的理由（`LONG_TURN` 拿掉了）。
    - 立刻送出（`!!` 開頭的訊息，`submit(now=True)`）：照常打字送出，Claude 忙時訊息會排隊並顯示「ctrl+x ctrl+s to send now」，`send_now()` 看到這行才按 `C-x C-s`。實測（2.1.289）：正在跑的 Bash 被移到背景，Claude 同一輪讀到訊息並回覆，`UserPromptSubmit` 在排隊時就已經觸發。
    - context 佔用：接頭的 `transcript.context()` 從對話紀錄最後一則主對話回覆的 `usage` 算（input + cache read + cache creation，跟 Claude Code 狀態列的算法一樣），視窗大小 `events.window()`：haiku 200k、其他 1M（2.1.289 狀態列輸入的 `context_window_size` 實測）。存在 `st["context"]`，顯示在頁尾和 `/status`；別台機器的由 `dcremote stream` 在 `Stop` 時算好帶回。
    - 訊息和回覆不是一對一（補充訊息共用一輪；背景工作完成會自己開一輪），所以規則是「每個 `Stop` 都貼」。Esc 中斷不會有 `Stop`。
    - 畫面只用在這幾個地方：啟動時回答信任資料夾的對話框、`!screen`／`!key`、判斷是否還在忙（`esc to interrupt`）、`/` 指令（例如 `/usage`）送出後回傳畫面，以及打字前偵測面板還開著就先按 Esc 關掉。面板的判斷是「看到 `Esc to cancel` 之類的提示，或畫面上沒有輸入框（橫線下一行以 `❯` 開頭）」：面板比畫面高時提示那一行會被擠出畫面，只認提示字樣會漏掉。Claude Code 改版後這些字樣可能會變。**機器人自己開的對話也照同一個原則（2026-10-09 起；使用者可以 `tmux attach` 直接坐在那裡，權限模式不是 bypass 時也會跳權限詢問）**：只有一般的輸入框有鍵盤時才打字、才按 Enter；`!` 模式或有對話框就不按任何鍵、在頻道說；只有機器人自己的指令打開的面板（`st["own_panel"]`，存在頻道狀態裡，機器人重啟後還在；任何一輪的事件一來就不算）才先按 Esc。跟接上的窗格不同的只有兩點：框裡留下的字照舊清掉（那是機器人自己的對話）；第一次按 Enter 前框裡的字跟打的對不上時照樣按（日誌印一行 `[enter] …`，並記進 `state/enter-differs.json`，doctor 的 `dcbot.enter-differs` 一週三次以上會 warn），免得 Claude Code 畫字的方式比對不認得時所有頻道都送不出去；回條沒到的重試只在框裡還是那則訊息時才按。上一則按了 Enter 卻還留在框裡時，自己的對話會清掉、重打、重送並在頻道說一句（接上的窗格不動、警告）。**畫面上固定字樣的判斷，一律只看 Claude Code 自己畫的區域**（manager 2026-10-09）：輸入框結束那條橫線以下（狀態列、面板提示；沒有輸入框時是畫面最後幾列），用 `screen.under_box()`；「在忙」只問 `screen.busy_shown()`，面板和對話框只問 `panel_shown()`／`pane_state()`。任何會出現使用者或 Claude 文字的地方（框上方的對話內容、輸入框裡的字）都不看：回覆引用「Esc to cancel」曾讓閒著的頻道所有訊息被擋，訊息自己寫到這幾個字曾讓它打進去後不按 Enter，內文寫到「[Pasted text]」曾被記成貼上。新增這類判斷、或審查它時，要用「內文自己含那些字」的訊息和回覆實跑。**接上的窗格（`/attach`、別台機器）是使用者自己的終端機，打字前不替他按鍵**（`may_type()`、`pane_state()`）：只有一般的輸入框有鍵盤時才打字；輸入框在 `!` 模式（打進去會當 shell 指令執行）、或有對話框／選單開著（權限詢問：打字加 Enter 等於選 Yes，Esc 等於選 No）就不打字、不按任何鍵、在頻道警告。只有機器人自己送的 `/` 指令或 `/btw` 打開的面板（`rt.own_panel`，任何一輪的事件一來就不算）才會先按 Esc 關掉。`/btw` 打字前走同一套檢查，打完之後框裡不只是它自己打的那段（`screen.bot_typed()`）就不清。接上的窗格每一次 Enter 之前（第一次、回條沒到的重試、`/btw`）都再讀一次畫面（`enter()`）：一般的輸入框、框裡正好是機器人打的那段才按；那台的事件連線斷著時不重試、也不算 `own_panel`。「正好是機器人打的那段」的比對（`screen.bot_typed()`）：空白不計、NFC、去掉 Claude Code 畫的時候會丟的字元；長訊息變成的 `[Pasted text #N]` 標記各代表一段（數量不超過 `screen.paste_marks()`，帶「+N lines」的是使用者貼的）；三列以上的框只比結尾（框會捲動）。已知限制：使用者在機器人打長訊息的那幾秒貼上單獨一長行、或打在被捲出畫面的上半段，看不出來。連發的訊息：框裡還是上一則剛按過 Enter 的字就等它消失（`rt.entered`，最多 5 秒）。
    - **`/btw` 的答案框、它的「x to clear history」、啟動時的對話框也只看 Claude Code 自己畫的地方（2026-10-11，#code-review-2 在 2.1.296 實跑出誤判後）**：答案框畫在輸入框原本的位置（所以有答案框時沒有輸入框），上緣是從最左邊開始的一列 `▔`，接著是問過的問題、縮排更深的答案，畫面最後一列是它自己的提示（結尾 `Esc to close`）；2.1.316 有些安裝畫成另一種：沒有 `▔` 那列，題目在上面的對話裡以使用者訊息「❯ /btw …」出現，問題縮排 2、答案縮排 4、提示列縮排 2（2026-11-03 在一個測試安裝上量到；v0.5.0 認不出，答案沒貼回、框沒關）。兩種都讀：`screen.edge_box()`、`screen.inline_box()`，樣本在 `screens/2.1.316/extra/T/`。`screen.btw_box()` 是唯一說「答案框在哪、裡面是什麼」的地方，`btw_answer()`、`btw_hint()` 只讀它。「答好了」只看答案框自己的提示列有沒有 `c to copy`（2026-10-12：請求失敗重試時那一列是 `· API error · retrying in 2s · attempt 3/10`，不是 `Answering…`，只認字會把重試中的框當成答案、把它關掉；樣本裡提示列有 `c to copy` 的恰好就是有東西可複製的）。沒答好的框機器人不按任何鍵：等到上限就說「還沒有答案、沒有關它」，下一則訊息送出前才關。啟動對話框（信任資料夾、bypass 警告）由 `screen.startup_key()` 判斷：沒有輸入框、最後一條橫線之後的列以「No, exit」和一個 Yes 兩個答案結尾（後面只能有提示列）才按鍵。對話內文、答案內文、使用者的訊息裡出現這些字都不算。真實畫面樣本在接頭的測試旁邊 `altention/tests/connectors/claude_code/screens/<版本>/`（同一個資料夾的 `samples.py` 讀），改讀畫面的函式要對著它們跑（`tests/test_screen_samples.py`、`tests/test_screen_words.py`）。
    - Claude Code 2.1.296 起不給 `--permission-mode` 時預設是 auto mode（狀態列「auto mode on」，工具直接跑不問），權限詢問多一項「Yes, and switch to auto mode」。機器人開的對話都明確帶 `--permission-mode`（頻道或安裝設定的值，C-121 之後沒有預設），不受影響；接上的窗格是什麼模式由使用者決定，機器人不判斷。
  - **print 模式**（`bot/claude_bridge.py`）：每則訊息跑一次 `claude -p --resume <session>`。是備用方案，tmux 模式出問題時用 `!mode print` 切過去。
