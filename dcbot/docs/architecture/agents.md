# 子代理和 workflow

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/agents.py`：子代理和 workflow 顯示成討論串。子代理自己的 API 請求失敗（Claude Code 發的是帶 `agent_id` 的 `StopFailure`，之後沒有 `SubagentStop`）只寫進它的討論串並收尾（狀態訊息「❌ 失敗（原因）」、workflow 的計數多「、N 個失敗」）、#audit 一行；主頻道不貼「這一輪中斷了」和［再試一次］、不取消開著的提問（#issues 30，2.2e）；沒有討論串的（已收掉、或 `AGENT_THREADS` 關）只有 #audit 那一行或什麼都沒有。失敗原因的字在 `events.failure()`（主對話的失敗和子代理的共用）。任務文字是子代理自己的對話檔的第一則：`SubagentStart` 的 hook 比那一列早（#issues 24），所以等子代理的檔出現的那個迴圈（次數和間隔是接頭的 `hooks.agent_waits`，最多 6 次 × 0.25 秒；本機 `agents.start` 在事件迴圈裡等、別台 `dcremote` 的 `enrich` 睡著等）同時等「第一則已經在檔裡」（`transcript.asked_yet`：等的是那一列，不是讀得出字：fork 型子代理的第一列是工具結果加一段 `<fork-boilerplate>`，濾完沒有任務文字，列在就不等；workflow 的代理若只寫了 harness 轉述使用者訊息的那一列，等帶任務的那一列），等滿了還沒有才照有的顯示。這段等待在本機是 `handle` 裡的 `await`、別台是 relay 裡的 sleep，等的時候別的頻道（那台別的對話）的事件也停著：量到四個子代理同時開、檔晚 0.08 秒出現時，別的頻道最多晚 0.25 秒（一次等待，四個的檔那時都在了），跟這一步之前相同。量到的（2.1.296，真的 workflow，樣本 `turns/2.1.296/w3-F.json`）：`SubagentStart` 的 hook 被叫到時那個代理的 `meta.json` 和 `.jsonl` 都還不存在，`meta.json` 約 0.02 秒後出現、`.jsonl` 0.04～0.08 秒後出現，而且一出現就已經有頭兩列。workflow 的代理在 `<對話>/subagents/workflows/<runId>/`。workflow 的代理（2.1.296）檔裡頭兩列 user：第一列是 harness 把觸發 workflow 的使用者訊息整段轉述（每個代理都一樣），第二列才是它自己的任務（`[Workflow harness — computed task] … The computed task text follows:`）；`transcript.first_prompt` 跳過 harness 沒帶任務的列、取帶任務的那一列的內文，找不到就照舊用第一列（#issues 28）。這兩列的字樣（`transcript.HARNESS`、`FOLLOWS`）是 2.1.296 的格式，改版時要對（接頭 `__init__.py` 列了哪些是「某一版的字樣」）；等不等只看結構、不看任務列的字樣（`transcript.asked_yet`）：第一個 user 列在了，而且它不是 harness 轉述那一列、或後面已經有第二個 user 列、或代理已經開始回話（assistant 列）→ 不等。任務列的字樣變了的話最壞是任務照第一列顯示，不會多等；只剩「轉述列的開頭還認得、第二列永遠不來」才等到上限。`SubagentStart`／`SubagentStop`、子代理內部的 `PreToolUse`（帶 `agent_id`）、`Workflow` 工具的 `PostToolUse`（帶 run id 和名稱）由它處理，不進主對話的進度。每個子代理一則狀態訊息加一個討論串；workflow 的代理（檔案在 `<session>/subagents/workflows/<run id>/`）共用一個討論串。過程從子代理自己的對話紀錄讀（接頭的 `transcript.new_texts(..., sidechain=True)`），累積後每 4 秒最多貼一則。討論串和訊息的 id 存在頻道狀態的 `rooms`／`subs`，機器人重啟後接得回來。`agent_type` 是空字串的 `SubagentStop` 是 Claude Code 自己的小幫手（例如提示建議），要忽略。
