# 封存

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/archive.py`：封存的頻道。`!detach` 不再刪掉頻道狀態，而是留下 `archived` 紀錄（窗格、tmux session、`home`、對話 ID、資料夾）。在封存頻道打字會給兩顆按鈕：接回原本的對話、在這裡開新對話。規則是一個窗格最多只接一個頻道：`/attach` 遇到有封存頻道記得這個窗格，就把那個頻道搬回來；按「接回」時窗格正被別的頻道接著，先問要不要移（移就先 detach 那個頻道）；窗格已經不在就用對話 ID 在同一個 tmux session 開新視窗接回。頻道重新設定（設定卡）時會清掉 `archived`。
  - **`/archive`**（C-63，2026-10-20）：`Archive.put()` 封存任何種類的頻道。對話：照 `!detach` 的格式留 `archived` 紀錄，但機器人開的視窗（`home`＋`pane`、機器人 server 上的 `tmux`）照閒置回收關掉（`close(kill=True)`，紀錄多 `tmux` 和 `kept`：permission、talk_limit 這些設定），接上的窗格只放開；正在跑（busy／bg）先問，按「還是封存」才做。其他種類（record、看板、files、terminal）狀態原樣留著，只加 `archived`（含 `kind`），terminal 先關 shell 視窗（有指令在跑不封存）；在封存分類打字給「恢復這個頻道」，把 `archived` 拿掉。每筆紀錄（`!detach` 的也是）記 `from`（原分類 {id, name}，None＝沒有分類）、`at`、`topic`，主題最前面加「📦 原分類：X · 封存於 日期」（`topic_with`），接回時 `home_category()`：原分類 id → 同名 → 照資料夾推算。封存分類是 `config.ARCHIVE_CATEGORY`、「<名> 2」…（`shelf()`：第一個不滿 50 的，全滿開下一個，空的不刪）；舊的「archive」分類也算封存分類（`LEGACY`）。`dcctl archive` 改成送 spool（`archive: true`），由機器人做，結果記在 #audit。每次啟動 `adopt_all()`（自己的 task）：封存分類裡沒有紀錄的頻道（手動搬進去的）照 `/archive` 補一筆（why `found_in_archive`，原分類從主題的註記讀；沒有註記就不寫 `from`，接回時照資料夾推算），舊「archive」分類裡的搬進「封存」。補記時只關閉閒置回收本來就會關的東西（機器人自己 server 上的 session）；你 tmux 裡的視窗只放開、終端機的 shell 不動（重啟後不知道它有沒有指令在跑），#audit 列出還開著的；`IDLE_HOURS` 內說過話或正在跑的對話這次不動，也列出來。「archive」分類空了只說、不刪。
  - **封存的頻道不再收它原本那個對話的事件**（2026-10-11，#issues 11）：機器人在這台開的視窗（`home`）卸下後環境裡還帶著 `DCBOT_CHANNEL`、`--settings` 裡還有回報的 hook，照樣會回報。`tmux_bridge.put_away(st)`（有 `archived`、沒有 `pane`／`tmux`／`home`）成立時 `handle()` 走 `let_go()`：不貼、不寫頻道狀態、不記逐輪的 #audit，只在第一次丟掉時記一行；`Ask` 馬上回絕（請它在終端機問）、`Plan` 交回終端機自己的對話框，免得 hook 等半天。事件照舊算處理完。接回（`Archive.back`）、`/attach`、設定卡之後狀態不再是封存，自然恢復。`!detach` 時還開著的提問和選單按鈕一併取消。接上的窗格和別台的視窗走路由表，卸下就拔掉，沒有這個洞（`tests/test_put_away.py` 釘住）。
  - **事件屬不屬於這個頻道，看的是「是不是這個頻道現在的那個視窗」，不是 `DCBOT_CHANNEL`**（同一天，#code-review 實跑出第二條路）：卸下後頻道被給了別的對話（「在這裡開新對話」、設定卡），就不再是封存，舊視窗的事件又貼進來，還把頻道的 `session_id` 改成舊對話的（下次重開會 `--resume` 到舊的，兩個行程接同一個對話）。`tools/dchook` 對「用環境變數認頻道」的事件多帶 `dc_pane`（`$TMUX` 的 socket 和 `$TMUX_PANE`；欄位名字要是機器人自己的：`source` 是 Claude Code 自己的欄位，SessionStart 用它說 startup／resume／clear，蓋掉會讓視窗裡 `/resume` 換對話後紀錄不貼；走路由表的 `--global` 不帶，那條本來就照窗格認）；`tmux_bridge.from_elsewhere(st, 正在開的視窗, ev)`：頻道有視窗（`pane`）就只收那個窗格的；`ensure_home` 開新視窗期間（`rt.opening`：先是 `True`，開好後是那個窗格）也收它的，因為 `SessionStart` 比 `st["pane"]` 寫進去早；頻道是機器人自己 tmux server 上的對話（`tmux`）就收那個 server 來的（同名的 session 關掉重開，新舊行程都是它的）；兩者都沒有的頻道沒有視窗，一律不是它的。**不看 session_id**：`/clear`、`/resume`、`--resume` 重開都是同一個視窗換 session，是頻道自己的。不是它的 → 照 `let_go()`，#audit 每個來源窗格記一次。沒有 `dc_pane` 的事件（不在 tmux 裡、別台、舊的）不判斷。
  - **hook 加的欄位不能蓋 Claude Code 自己的**（2026-10-11）：`tools/dchook` 新加的欄位一律 `dc_` 開頭（`OURS_PREFIX`）；規矩之前就有的六個（`channel`、`ts`、`hint`、`send_to`、`send_text`、`started`）列在 `OURS_BEFORE`；`tools/dcremote` 加的列在它的 `ADDED`。`tests/test_hook_fields.py` 拿真實的 hook 內容（`altention/tests/connectors/claude_code/hook_payloads/<版本>/`，Claude Code 交給 hook 的原樣）驗：Claude Code 給的每個欄位原樣到達（只有 `tool_input`、`tool_response` 拿掉、過長的回覆截斷並註明），我們加的名字沒有一個跟它的撞。Claude Code 改版多了欄位就補一份樣本重跑。
  - 機器人開的視窗卸下後又用 `/attach` 接回來時，它自己 `--settings` 的 hook 和全域 hook（路由表）都會回報同一件事：`dchook` 在「用環境變數認頻道」那條路發現這個窗格也在路由表裡就不寫（提問的 `--ask`／`--plan` 也不出聲），只留路由表那一份。
