# 提問、/btw、一輪的範圍

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/ask.py`：Claude 的 AskUserQuestion 工具（在終端機會開選單，Discord 上沒人能操作）。`state/claude-settings.json` 另外為這個工具掛了 `dchook --ask`：它把題目寫成 `Ask` 事件後**等著**，`ask.py` 把每一題貼成一則訊息（選項是按鈕，複選或選項多是下拉選單，另有「其他…」開輸入框），全部答完後把答案寫到 `state/answers/<id>.json`，hook 讀到就以「允許 + 改寫工具輸入（加上 `answers`）」回給 Claude Code，工具直接帶著答案回傳，選單不會出現。只剩一題沒答時，頻道裡打的字直接當答案（`Asker.typed()`，`main.deliver()` 送進 tmux 之前先問它；計畫不適用）。按鈕靠 `custom_id`（`ask:<id>:<第幾題>:<選項>`）在 `on_interaction` 裡辨認，等待中的題目記在 `state/asks/`，所以機器人重啟後按鈕照樣有效。`!stop`、`!reset`、這一輪結束都會把還開著的題目標成已取消。plan mode 的「要不要照計畫執行」走同一套：`PermissionRequest`（matcher `ExitPlanMode`）掛 `dchook --plan`，貼出計畫和兩顆按鈕。核准時 hook 回 `{"behavior": "allow", "updatedInput": 原本的工具輸入}`，**少了 `updatedInput` 終端機的對話框不會關**；要修改就回 `deny` 加上使用者寫的話。用 `PreToolUse` 回 allow 沒有用，對話框照樣跳出來。**在終端機取消（C-152）**：提問或計畫等答案時在終端機按 Esc、Ctrl-C（`!key` 也一樣），Claude Code 只對等答案的 hook 送 SIGTERM，不會有 Stop 或任何其他事件（2.1.317 實測）。`dchook` 在 `wait_answer` 期間攔 SIGTERM／SIGHUP／SIGINT，寫一個 `AskCancelled` 事件（帶 ask_id，跟其他事件一樣先寫暫存檔再改名）後馬上結束；機器人收到（`ASK_CANCELLED`）由 `Asker.cancelled()` 關掉那一題：還沒答的那幾則改成「→ （在終端機取消了，沒有回答）」、刪紀錄、`on_done` 改寄件頻道的 ⏸️、#audit 一行，不交任何東西給 hook。先到的算數：已經答完、關掉、別的頻道的或不認得的 ask_id 什麼都不改，只記一行 #audit；`settle()` 在改完訊息後再看一次紀錄還在不在（取消剛好插進來就不收這個答案，`typed()` 回 False，那則訊息照常送給 Claude）。舊版機器人看到 `AskCancelled` 是 UNKNOWN：在碰任何頻道狀態之前就略過，只寫一行 log。
- `/btw`：`tmux_bridge.btw_open()` 在頻道開一個討論串，`btw_ask()` 把問題（加上這個討論串先前的問答，`events.btw_prompt()`）打成 `/btw …`，從畫面上的答案視窗讀回答案（`screen.btw_answer()`），貼進討論串。討論串裡的訊息由 `main.on_message` 轉給 `btw_ask()`；問答記在頻道狀態 `btw`。答案優先用答案視窗的「c 複製」讀（tmux 要開 `set-clipboard on`，機器人自己的 tmux server 會自動開；使用者自己的 tmux 不去改，那時退回讀畫面），完整而且保留 markdown。`/btw` 自己有跨題記憶，答案視窗累積兩題以上時會出現「x to clear history」，讀完就按 x 清掉，讓各討論串分開；只有一題時清不掉，所以換討論串的第一題會在題目裡註明「和先前其他 /btw 無關」。關答案視窗按 Esc 之後**一定要等視窗消失**才放開鎖：Esc 還沒生效時若又按一次，第二下會打到正在跑的那一輪、把它中斷。主對話忙的時候 `close_panel()` 也不按 Esc。
- **一輪是哪一輪、頁尾算誰的**（2.2e，#issues 27）：`Turn.pid` 記這一輪事件的 `prompt_id`；帶著別的 `prompt_id` 的輸入／工具／結束／失敗事件到了，還開著的那一輪就是沒有事件就結束的（Esc 中斷：Claude Code 不發事件），先收掉再處理（`another_turn()`），所以被中斷那一輪的工具次數和秒數不會算進下一輪的頁尾。`watch_busy()` 看到畫面三次沒在忙時只是「歇著」（`rest()`：不再顯示輸入中、收掉「處理中…」訊息、`Turn.quiet`），**不丟掉那一輪**：它可能卡在權限對話框幾分鐘後繼續，結束時頁尾照樣有工具次數和秒數（含等的時間）；窗格不在了才是真的結束。沒有 `prompt_id` 的版本：歇著之後使用者的下一句話算新的一輪。**一輪的結束等自己那一列（2.2f）**：Claude Code 先叫 Stop 的 hook、約 0.1 秒後才寫這一輪最後回覆的列（實量：真的 API 79 輪，dchook 的 `ts` 之後 0.083–0.107 秒；跟 hook 跑多久無關），而頁尾的 context 就是從那一列的 usage 讀的。以前 Stop 一到就處理：新對話第一輪沒有 context、之後每一輪顯示的是上一輪的。現在接頭的 `hooks.awaits()` 對 `Stop` 也回「先留著」，直到對話檔裡從讀到的位置往後出現這一輪的 `hooks.last_reply()` 列（assistant、不是側鏈、帶 usage、`stop_reason` 是 `end_turn`；同一個回覆每個內容塊各一列、同時寫、都帶同樣的 usage，看到任何一列就夠；被截斷（max_tokens）或被拒（refusal）的列不算，Claude Code 自己會再問；`stop_reason` 是別的（例如停在 stop sequence 的正常回覆）時，文字等於事件的 `last_assistant_message` 也算；API 錯誤的列（`isApiErrorMessage`）不算）；最多等 `END_HOLD_SECS` 0.5 秒（從事件的 `ts` 算，積著沒人看的事件不等），到了照有的做並計數（`hooks.ends_late()`；只計「等過而沒等到」的：第一次被看到時已經超過上限 `LATE_WITHIN` 2 秒以上的舊事件不計；機器人第一次在 supervisor.out 留一行、次數寫在 `state/turn-ends-late.json`，doctor 還沒讀）。**不等的**：沒有 `last_assistant_message` 或它是空字串的 Stop（模型回空，不會有那一列）、`StopFailure`（它的列也晚 0.1 秒，但失敗訊息不顯示 context）、子代理的事件、沒有 `prompt_id` 或 `ts` 的、還沒見過的對話檔。是哪一輪的列：這一輪自己第一列（`promptId` 等於事件的 `prompt_id`）之後的，找不到第一列時比對文字（事件的 `last_assistant_message` 只有回覆**最後一個文字塊**、而且去了頭尾空白）。留著的方式跟 1.6b 的工具列相同（本機留在 spool、同頻道後面的排在後面、別的頻道照走；別台是 `dcremote` 的 relay 用同一個函式，有東西留著時 stream 0.1 秒後再看）；`INTERIM` 關掉時工具列不等、結束仍然等（`awaits(calls=False)`）。量到的事實和樣本在 `altention/tests/connectors/claude_code/turn_ends/`。
