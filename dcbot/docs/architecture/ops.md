# 工具、重開、上線、看門狗

從 `dcbot/CLAUDE.md` 的「架構」搬來，原文沒改（2026-11-19）。路徑相對於 `dcbot/`；接頭指 `altention/connectors/claude_code/`。

- `bot/util.py`：純函式（例如切 Discord 訊息），方便測試。
- `tools/dcctl`：管理 Discord 的命令列工具（標準函式庫，REST API）。**不在機器人那台時整個指令轉給那台**（C-109）：在 `from bot import config`（會讀設定檔）之前先跑 `altention/dc/botside.py` 的 `hand_over()`，機器人在別台就把 argv（只有 `post`、`edit` 帶 stdin）經 ssh 交給那台的 dcctl，結束碼和輸出原樣傳回；連不上就說連不上哪台，不退回本機的 token。「機器人在哪台」只問 `botside.bot_machine()`（C-53 待命接手以後只換這一處），`altention dc post`／`read`／`notify` 也都經過 `botside.run()`：先用 `ssh <別名> true` 找路（可以換別名），指令只送一次，255 不重送（可能已經做了）。轉過去的指令帶 `ALTENTION_HANDED=1`，那台若也認為機器人在別台就拒絕，不會兩台互轉。`dcctl check [--json]`：問一次 `GET /users/@me`，doctor 在機器人那台用它報 token 失效（`dcbot.token`）；別台 doctor 跑 `botside.py --reach` 報轉不轉得過去（`dcbot.forward`），別台留著設定檔只看在不在、不打開（`dcbot.standby-token`，warn，不叫人刪：待命機器要留）。`dcctl app [--json]`（C-54a）：機器人自己的 application，Activities 開了沒（flags 的 EMBEDDED，1<<17）和插件要的 ID（application、擁有者、伺服器），不印 token、不寫 #audit。新的 Discord 管理功能優先加在這裡。`dcctl history <頻道>` 讀頻道最近的訊息：新對話要知道先前講了什麼、或要確認訊息有沒有送達時用。固定的看板（釘選、原地更新的訊息）：`dcctl pin <頻道> <訊息 ID>`（`--unpin` 取消）、`dcctl edit <頻道> <訊息 ID>`（新內容從 stdin；只改機器人自己發的；超過 2000 字報錯，不截斷不拆）。`dcctl send-json <頻道>`（C-156 a，給 #discord-lab 的樣品）：stdin 的 JSON 是一則訊息的 payload，原樣 POST 到那個頻道或討論串（Components V2 的 flags 32768 由 Discord 決定收不收），只有 `allowed_mentions` 一律換成 `{"parse": []}`；只發、不改不刪；每則記一行 #audit；C-172a P1b 第 4 批起它和 `dcctl edit` 都經機器人：dcctl 照舊先檢查，寫進貼文佇列（`raw`，edit 另帶 `edit_message`），機器人的 `posts.from_dcctl()` 再檢查一次（`bot/rawpost.py`：保留字首、冒用 📨 卡、一律不 @；edit 只收文字、只改 `bot/sentids.py` 記著的），經 `deliver(raw=, via=bot.http)` 原樣 POST／PATCH，記 ledger、記住 ID 給 dcctl edit、寫 #audit（字跟以前 dcctl 寫的一樣）；dcctl 等收據最多 `QUEUE_WAIT` 20 秒，沒等到印「機器人還沒處理到，已排著，會送，不用重送」、結束碼 3，Discord 不收是 4。`dcctl send` 照舊直連（supervisor 在機器人停著時用），送完在 ledger 旁的 `ledger-pending/` 留一個小檔（`bot/pending.py`，先寫暫存再 rename），機器人每一圈（`posts.tick`）讀進 ledger，讀不懂的移到 `ledger-pending-bad/`。dcctl 自己還直接發的只剩 send、它自己的 #audit 行和 `dcctl guide`（`tests/test_dcctl_queue.py` 的例外清單）；不在機器人那台時 stdin 跟著轉過去（`botside.STDIN_COMMANDS`）。
- 機器重開：cron 的 `@reboot` 和每 5 分鐘那一行會把 `supervisor.py` 帶起來；tmux 對話會消失，機器人啟動時發現「狀態寫著在忙或有背景工作，但 tmux 不在了」會在該頻道通知，下一則訊息自動用 `--resume` 接回。
- `bot/catchup.py`：機器人離線時（部署、重啟）擁有者發的訊息 Discord 不會補給機器人。每個頻道記著處理過的最新一則擁有者訊息（`state/seen.json`，`on_message` 一開頭 `mark()`），上線後讀之後的歷史交給 `on_message`；**每次 `on_ready` 都補**（C-170：斷線太久，gateway 重連開的是新 session，Discord 不補送；`on_disconnect` 時 `cut()` 記下起點（已經有一個在等就留著舊的），`on_resumed` 時 `resumed()` 丟掉（續上的 session Discord 會補送），同時只有一個補收在跑（`lock`））；`WINDOW`（30 分鐘）以前的只列出來不送。讀的起點用啟動當下的快照（`at_start`），因為補讀前就到的即時訊息會把 `seen` 往後推；同一則不會處理兩次（`handled`）。**補收只做一般訊息和 `REPLAYED` 清單裡的唯讀指令**（C-124，manager 2026-11-03 定白名單：`!help`、`!status`、`!recap`、`!screen`、`/btw`）；其他指令（第一個字是 `!` 開頭但不是 `!!`，或 `/` 加名稱）一律不做、標成處理過，在頻道說「離線時收到的 X 沒有執行，要的話再送一次」（`ONE_BY_ONE` 3 則以內一則一行，更多合成一則列前 `LISTED` 5 則和總數，`told()`），#audit 那行附數字。終端機頻道每一則都是 shell 輸入，補收時除了清單裡的一律不跑。新增的指令預設不補做，確定只看不改才加進清單（`tests/test_catchup.py` 對著 `main.BUILTINS` 檢查）。
- 「上線」的定義（`state/ready`，supervisor 據此判斷新版本好不好）：登入成功還不夠。`Bot.self_test()` 啟動時用真的 `tools/dchook` 送一個假事件（頻道 `selftest`），`pump()` 從佇列讀到才呼叫 `Bot.ready()` 寫 `ready`。hook → 佇列 → pump 這條路壞了，新版本就不會被當成好的，3 分鐘後自動退回。`deploy.sh` 部署前也先拿樣本實際跑一次 `dchook`，沒寫出事件就停止部署。
- `supervisor.py`：看門狗（只用標準函式庫，不 import 引擎的任何東西）。新版本 3 分鐘內沒上線、啟動就當掉、或試用期內有 2 個以上事件處理失敗（`state/events-bad/`；因為網路或 Discord 出錯的存成 `*.net.json`，不算），會自動退回上一個正常版本。「版本」是 `dcbot/` 加 `altention/` 的 tree（只有這兩處變了下次啟動才算試用）；機器人正常在跑時 `last_good` 會跟著 HEAD 前進（版本沒變的前提下），所以退回只退掉試用期那次部署帶進來的東西。退回的是**整個引擎的樹**（一起跑過的組合），commit 訊息和通知列出被退掉的每個 commit；good 到 HEAD 之間動過 `.gitignore`／`.gitattributes`、或有路徑現在是連結或被忽略（搬進實例）時改成只退 `dcbot/` 和 `altention/`，並註明「部分退回」要人處理。別的頻道在被退回的檔上沒提交的修改先另存到 `.git/altention-saved/<時間>-rollback/`。退回時拿共用的 git 鎖（等 120 秒，等不到照做），在子行程用退回後的 `altention.sync.update` 接到遠端上（有逾時；子行程怎麼壞都改用標了 `agent-rebase` 的普通 rebase，衝突就中止）；所有 git 都有逾時，網路卡住也照樣啟動機器人。**搬移類的 commit（`instance.py move-apply`）不要同時改 `dcbot/` 或 `altention/`**，免得它觸發試用。換掉跑著的 supervisor 和它壞掉時怎麼救：`SUPERVISOR-RESCUE.md`。
